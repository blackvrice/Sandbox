# 13. 테스트 전략

> **규범 문서.** 변경을 검증하는 방법과 골든 해시 절차를 정합니다.
> 상태: L1·L1′·L2(content)·L3(D1·D2·D4)·L4(짧은)·L6 가 구현됨 (Phase 1~5A). 2장 표 아래 목록이 현재 등록된 테스트입니다.

---

## 1. 원칙

```text
안전망이 기능 코드보다 먼저다. (RTS ADR-0005 계승)
"동작이 같다"를 명령 하나로 증명할 수 없으면 리팩터링이 아니라 재작성이다.
```

## 4. sbx_sim_check (결정론 하네스)

RTS `rts_sim_check`의 인터페이스를 계승합니다.

**Phase 3 구현** (`tools/sim_check/`, CMake 옵션 `SBX_BUILD_TOOLS`, 기본 ON):

```text
sbx_sim_check [--scenario random_walk_1k] [--seed N] [--ticks N]
              [--hash-every 30 | --hash-at 30,90] [--print-hash]
              [--repeat N]                       D1 — N 개 월드를 나란히, 체크포인트마다 비교 + 진단
              [--save-at T [--save-dir D]]       D2 — T 틱 뒤 저장→로드한 월드를 나란히 끝까지 비교 (Phase 4)
              [--golden <file> | --record-golden <file>]   D4 — 툴체인별 항목 (ADR-0012)
              [--profile] [--list-scenarios] [--inject-divergence T]
              [--content-root DIR] [--validate-content 팩[,팩]]   (Phase 5A) 콘텐츠 루트 · 검증만 (오류면 종료 코드 1)
종료 코드: 0 통과, 1 불일치, 2 입력 오류, 3 골든에 이 툴체인 항목 없음 (CTest SKIP)
(Phase 5C) --replay-roundtrip [--replay-dir D]: 시작 상태를 D/start 에 저장하고 적용 명령·해시를 D/replay.sbxr 로 기록한 뒤,
               세이브를 로드해 재생하며 비교 (D3). --replay F: 기록된 리플레이 검사만. --require-prefabs a,b: 끝에 0 이면 실패.
(Phase 5B) --threads n[,n..]: 첫 값으로 기본 실행(--repeat 개)을 돌리고, 나머지 값마다 실행을 하나씩 더해 나란히 비교한다 (D5).
               실행마다 자기 JobSystem 을 가진다. 기본 0 (Worker 없음 — 그 자리에서 계산).
```

아래는 최종 목표 인터페이스입니다 (`--world`, `--replay-roundtrip`, `--commands` 는 `[계획]` Phase 5C).

```text
sbx_sim_check --world <path|scenario> [--content <pack>] --ticks N
              [--hash-at 0,30,90 | --hash-every 30] [--print-hash]
              [--golden tests/golden/<name>.json]          D4
              [--repeat]                                    D1: 같은 입력 2회 실행 비교
              [--save-at T]                                 D2: T 에서 저장→로드→이어서 N 까지, 비교
              [--replay-roundtrip]                          D3: 기록→재생 divergence 검사
              [--threads 0,1,8]                             D5: 워커 수별 비교
              [--commands <log>]                            명령 로그 주입
              [--validate-content <pack>]                   콘텐츠 검증만
              [--verbose]
실패 출력: 첫 불일치 틱 → 엔티티(saveId, prefab) → 컴포넌트(stableId) → 필드(경로, 기대값, 실제값)
           + 의심 범주 (순회 순서 / 난수 / 부동소수 / 저장 누락)
종료 코드: 0 통과, 1 불일치, 2 입력 오류
```

## 5. 골든 해시

**Phase 3 형식** (`tests/golden/random_walk_1k.json`, [ADR-0012](adr/0012-golden-hash-per-toolchain.md)) — 실행 조건은 파일에,
해시는 툴체인 키(`<System>-<processor>-<CompilerId>-<major>`, `foundation/BuildInfo.hpp` 의 `kToolchainKey`)별로:

```jsonc
{
  "scenario": "random_walk_1k", "seed": 1, "ticks": 600, "hashEvery": 60,
  "entries": {
    "Linux-x86_64-Clang-19": { "simVersion": 1, "compiler": "Clang 19.1.1", "hashes": { "60": "0x…", "600": "0x…" } },
    "Linux-x86_64-GNU-13":   { … }
  }
}
```

```text
기록   sbx_sim_check --record-golden tests/golden/random_walk_1k.json   (이 툴체인 항목만 쓰거나 바꾼다)
       Windows 에서 처음 실행하면 det_random_walk_golden 은 SKIP 이다 → 위 명령으로 기록해 커밋한다.
비교   항목 없음 → 3 (SKIP), simVersion 다름 → 1 ("다시 기록"), 해시 다름 → 1
관찰   2026-10-05: Clang 19 와 GCC 13 (Linux x86-64), Debug 와 RelWithDebInfo 가 모두 같은 해시였다 (simVersion 1·2 모두).
       그래도 항목은 따로 둔다 — 보장 범위는 같은 바이너리다 (ADR-0004).
```

초안 형식 (참고, Phase 5 의 콘텐츠·세이브 기반 시나리오에서 필드가 늘어난다):

```jsonc
// tests/golden/ecosystem_small.json
{
  "scenario": "tests/data/worlds/ecosystem_small",
  "content": "tests/data/content/ecosystem",
  "ticks": 900,
  "simVersion": 1,
  "hashes": { "0": "0x…", "300": "0x…", "900": "0x…" },
  "recordedAt": "YYYY-MM-DD",
  "recordedBy": "<commit>",
  "note": "의도적으로 시뮬레이션 동작을 바꾼 커밋에서만 갱신한다."
}
```

```text
기록 절차
  1. --repeat 통과 확인 (비결정적인 코드를 골든으로 박지 않는다)
  2. --print-hash 출력의 hashes 를 옮겨 적고 recordedAt/recordedBy 기입
갱신 규칙
  리팩터링 커밋        해시 동일 필수. 다르면 리팩터링이 동작을 바꾼 것 → 그 커밋에서 해결
  규칙 변경 커밋       kSimVersion++ 와 골든 갱신을 같은 커밋에, 메시지에 이유
  시나리오(입력) 변경 커밋  simVersion 은 그대로, 모든 툴체인 항목을 다시 기록하고 메시지에 명시 (04 6장 예외)
  골든 파일의 simVersion 과 코드 kSimVersion 이 다르면 det_*_golden 은 "갱신 필요"로 실패한다
  (RTS 에서 simVersion 2 전환 후 골든이 1로 남았던 상태를 구조적으로 막는다)
```
