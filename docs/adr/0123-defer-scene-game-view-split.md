# ADR-0123. ST-06-11 (Scene/Game 뷰 분리 · 떼어 낸 창) 을 v0.12 로 미룬다

- 상태: **Accepted** · 날짜: 2026-11-11
- 관련: [ADR-0118](0118-studio-shell-dockspace-design-system.md) (셸 · 모드 띠), [ADR-0096](0096-roadmap-versioning-small-milestones.md) (작은 MINOR),
  [29-STUDIO-UI](../29-STUDIO-UI.md) 1 · 2장, [25-STUDIO-ARCHITECTURE](../25-STUDIO-ARCHITECTURE.md) 4장, task-registry ST-06-11

## 맥락

v0.8 의 마지막 남은 구현 태스크 ST-06-11 (P3, 완료 기준 수동 QA) 을 조사했다 (2026-11-11):

```text
1. 게임 카메라가 없다 — 카메라는 Camera2D 하나 (편집 카메라 = 보는 카메라). Game 뷰를 따로 그려도 Scene 과 같은 그림이다.
   뜻 있는 Game 뷰는 콘텐츠의 게임 카메라 정의 (따라갈 엔티티 · 범위 · 비율 — 11 스키마) 가 먼저다
2. Renderer 는 한 프레임에 한 번 record 하는 전제 (업로드 링 · GPU 타임스탬프 칸 · 마지막 카메라). 두 뷰는 뷰마다 링 · 타임스탬프를 나누고,
   오프스크린 RenderTarget 텍스처를 ImGuiRenderer 표에 바깥 텍스처로 등록해야 한다 (06 · ADR-0020 · 0023 변경)
3. 떼어 낸 창 (ImGui 멀티 뷰포트) 은 플랫폼 창 층 (Win32 · X11 · Cocoa) 의 다중 창과 백엔드마다 창별 스왑체인이 필요하다 (07)
4. 완료 기준이 창 QA 인데 지금 창 QA 자체가 밀려 있다 (UI-4 — 29 7장)
```

v0.8 의 목표 (CLI 없이 만들고 · 열고 · 빌드하고 · 돌린다 — releases v0.8) 는 같은 뷰 + 모드 띠 (UI-1) 로 이미 채워진다.

## 결정

```text
1. ST-06-11 의 목표 버전을 v0.8 → v0.12 (Advanced Creator Tools) 로. P3 그대로 — v0.12 시작 때 다른 P2 · P3 와 함께 필요성을 판정한다
2. 다시 할 때의 차례: (a) 게임 카메라 콘텐츠 정의 (스키마 · 결정론 밖 — 표현만) → (b) 오프스크린 Game 뷰 창 (편집 오버레이 없음 · 게임 UI ·
   고정 비율) → (c) 떼어 낸 창 (멀티 뷰포트). (c) 는 따로 판정해도 된다
3. v0.8 의 남은 일 = UI-4 창 QA (사람 손) 와 릴리스 준비 (0.8.0)
```

## 근거

```text
- 비용 대비: 렌더러 · 플랫폼 · 콘텐츠 스키마 세 곳을 바꾸는 P3 를 검증 못 한 채 넣으면 v0.8 릴리스를 막는 위험만 늘어난다
- 같은 뷰 + 모드 띠는 Roblox · Godot 의 쓰는 모양과 같다 (29 2장 Adapt) — 분리는 편의
- 게임 카메라는 v0.12 의 다른 태스크 (타일맵 · 애니메이션) 가 같이 쓸 표현 개념이다
```

## 결과

- 얻는 것: v0.8 범위가 닫힌다 (구현 태스크 모두 Done — 창 QA 만), 렌더러 변경을 카메라 정의와 함께 한 번에.
- 포기하는 것: v0.8 의 Game 뷰 · 다중 모니터.
- 위험: 없음 (기존 동작 그대로).

## 재검토 조건

v0.12 시작 판정, 게임 카메라 · 화면 비율이 필요한 템플릿 (M6-T2) 이나 Creator 요청, 플랫폼 창 층의 다중 창 지원.
