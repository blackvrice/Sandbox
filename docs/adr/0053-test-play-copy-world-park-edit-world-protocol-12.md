# ADR-0053. 테스트 플레이 — 편집 월드는 서버 메모리에 그대로 맡기고 복사본으로 플레이, 멈추면 되돌린다 (프로토콜 12)

- 상태: **Accepted** · 날짜: 2026-10-20
- 관련: [ADR-0031](0031-world-ops-generation-replay-playback.md) (세이브 · 로드 · 리플레이 — WorldOp · WorldChanged · generation),
  [ADR-0046](0046-game-control-command-restart-reopens-entry-world.md) (게임 시작 · 재시작), [10-EDITOR](../10-EDITOR.md) 9장,
  [08-NETWORK](../08-NETWORK.md) 5장, [18-PLATFORM](../18-PLATFORM.md) 5.1 (M5-T1), [플랫폼 초안 architecture/03](../platform/architecture/03_EDITOR_AND_NOCODE.md) 2장

## 맥락

v0.2 M5-T1 "Test Play: 편집 월드의 메모리 스냅숏에서 분기 세션, Stop 이면 버리고 원본 그대로 (선택 저장)". 지금은 편집하던
월드에서 바로 게임을 시작하면 (GameControl) 플레이가 편집 결과를 바꾸고, 되돌리려면 저장 · 불러오기를 손으로 해야 한다. 초안 2장:
Test Play 는 편집 월드에서 분기한 게임 세션, 끝나면 실험 상태를 버리거나 골라 저장. 정할 것:

```text
1. 원본을 어떻게 지키나 (스냅숏의 형태)      2. 플레이 월드를 어떻게 만드나      3. 게임 시작 · 일시정지
4. 그 동안의 다른 요청 (저장 · 불러오기 · 재시작 · 기록 · 자동 재시작)        5. 와이어 · UI
```

## 결정

```text
1. 원본 = 편집 월드의 runner 객체 그 자체를 서버 메모리에 맡긴다 (ServerHost::m_editRunner — 돌리지 않는다). 멈추면 그 객체가
   돌아오므로 틱 · 일시정지 · 오버레이 · 진행 중이던 경로 Job 까지 시작 전과 같다 (세이브로 담지 않는 상태도). 스냅숏을 다시
   읽어 되돌리는 것이 아니라 바꾸지 않은 원본을 쓴다.
2. 복사본 = 원본을 임시 폴더에 저장하고 다시 연 것 (persist::saveWorld → scenario::openSave — 세이브 · 로드와 같은 길이라 해시
   검증 · 오버레이가 그대로). 폴더는 바로 지운다. 메모리 안 직렬화 (폴더 없는 세이브) 는 [계획] — 같은 형식을 두 번 만들지 않는다.
3. 게임 프로젝트 (gameMode) 면 복사본의 세션을 Lobby 로 놓고 (resetSession) 서버가 GameControl Start 를 넣는다 (카운트다운부터).
   복사본이 일시정지였으면 서버가 ResumeSimulation 을 넣는다. 게임 모드가 없으면 복사본이 돌기만 한다.
4. 테스트 플레이 중: 불러오기 · 리플레이 재생 · 게임 재시작 · 기록 시작은 거절 ("먼저 멈추십시오"), 저장은 된다 (플레이 결과를 골라
   남기는 "선택 저장"). 자동 재시작 (GameMode.restart auto) 은 하지 않는다 — 끝난 판을 보고 멈춘다. 복사본에 대한 편집 명령은
   그대로 적용되고 멈추면 버린다. 시작 · 멈춤 권한 = 다른 월드 요청과 같은 시뮬레이션 제어 열 (Admin 부터).
5. 와이어 (프로토콜 11 → 12): WorldOp op 8 TestPlay · 9 TestStop (이름 무시), WorldChanged reason 4 TestPlay · 5 TestStop,
   ServerStats mode 3 = 테스트 플레이. 바뀔 때마다 generation 이 오르고 모두가 새 월드를 받는다 (불러오기와 같다).
   클라이언트 "월드" 패널에 "테스트 플레이" / "테스트 플레이 멈추기 (되돌리기)" 단추와 상태 줄.
```

시뮬레이션 · 세이브 형식 · kSimVersion 그대로 (서버가 월드를 바꾸는 방식만 늘었다).

## 근거

```text
- 원본 객체를 맡긴다: "원본 오염 없음"을 가장 확실하게 지킨다 — 다시 읽은 월드는 세이브에 담지 않는 상태 (경로 Job · 편집
  순번 · 역할 상태) 가 다를 수 있다. 메모리 비용은 월드 하나 (편집 중인 월드는 보통 작다).
- 복사본은 세이브 · 로드 길: 이미 해시 검증으로 결정성이 증명된 길이다. 월드 복사 생성자는 Registry · 색인 · 경로 · 콘텐츠 포인터를
  모두 깊게 복사해야 해 위험이 크다.
- 재시작 · 불러오기 거절: 맡겨 둔 원본과 세 번째 월드가 섞이면 무엇으로 돌아갈지 모호하다. 저장은 원본을 건드리지 않는다.
```

## 결과

- 얻는 것: 편집 → 테스트 플레이 → 멈추기 → 그대로 편집 계속. 플레이 결과가 마음에 들면 멈추기 전에 저장.
- 포기하는 것: 메모리 직렬화 (임시 폴더를 쓴다), 테스트 플레이 중의 기록 · 재시작, 여러 사람이 각자 테스트 플레이 (서버 월드는 하나).
- 위험: 맡긴 월드 하나만큼 메모리. 서버가 테스트 플레이 중에 끝나면 원본은 저장되지 않는다 (편집 내용은 그 전에 저장해야 한다).

## 대안

| 대안                                          | 기각 사유                                                                  |
|-----------------------------------------------|----------------------------------------------------------------------------|
| 스냅숏 저장 → 멈추면 그 스냅숏을 불러온다     | 세이브에 없는 상태가 달라질 수 있고, 다시 읽는 비용이 든다                 |
| SimulationWorld 복사                          | Registry · 색인 · 경로 · 콘텐츠를 깊게 복사 — 결정성 위험이 크다             |
| 별도 서버 프로세스로 테스트 플레이            | 접속을 옮겨야 하고 단일 플레이 · 에디터 흐름이 끊긴다                      |
| 클라이언트만의 로컬 플레이                    | 서버 권위 · 멀티 편집과 맞지 않는다                                         |

## 재검토 조건

메모리 직렬화가 생길 때 (GamePackage — M5-T2), 여러 사람이 각자 테스트 플레이해야 할 때 (방 · 세션 — v0.7).
