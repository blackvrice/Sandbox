# ADR-0016. 리플레이는 tick() 호출 번호로 명령을 놓고 saveId 로 대상을 적으며, 읽기 전용 System 패스는 Worker 와 나눈다

- 상태: **Accepted** · 날짜: 2026-10-06
- 관련: [09-SERIALIZATION](../09-SERIALIZATION.md) 4장, [04-DETERMINISM](../04-DETERMINISM.md) D3·D5·7장,
  [03-SIMULATION](../03-SIMULATION.md) 0장, [ADR-0015](0015-ai-tick-caches-saveid-refs-path-jobs.md)

## 맥락

Phase 5C 에서 리플레이(D3)와 1만 개체 성능 기준을 다뤘다. 정할 것이 셋이었다.

```text
1. 명령의 "위치": 문서 초안은 (tick, editSequence). 일시정지 중의 편집 단계는 틱 번호가 같고, 재생이 명령을 미리 큐에
   넣으면 실행 중인 같은 틱의 Stage 2 가 편집 단계 몫까지 한꺼번에 가져가 순서가 바뀐다.
2. 명령의 대상: NetEntityId 는 세션 값이다. 리플레이의 시작점은 세이브이고, 로드한 월드는 netId 를 다시 매긴다.
3. 형식: 문서 초안은 바이너리 SimCommand. 명령의 바이너리 코덱(비트스트림)은 와이어 포맷과 함께 Phase 9 에 온다.
4. 성능: ecosystem_10k 에서 감지(Stage 6)가 틱의 절반 — 엔티티마다 독립적인 읽기 전용 계산이다. System 안 병렬화는
   Phase 15 계획이지만 JobSystem 이 이미 있다.
```

## 결정

```text
1. 명령 레코드는 call(기록 시작 뒤 몇 번째 tick() 호출인가)에 놓는다. 재생은 call 마다 그 call 의 명령만 큐에 넣고
   tick() 한 번 — 헤더는 (executeTick 0, issuer 0, 기록 순번)이라 그 호출에서 기록 순서대로 바로 적용된다.
   editSequence 는 진단용으로만 남긴다.
2. 대상은 saveId 로 적는다. SimulationWorld 가 명령 관찰자에 페이로드를 넘기기 전에(적용 전에) netId → saveId 로 바꾸고,
   재생이 그 월드의 netId 로 되돌린다. 수락된 명령만 기록한다.
3. replay.sbxr = JSON Lines (머리 · cmd · hash · end). 명령 JSON 은 core/command/CommandJson (op 으로 구분). replayVersion 1.
   바이너리는 Phase 9 의 비트스트림과 함께 replayVersion 2 로.
4. 엔티티마다 독립적인 **읽기 전용** 패스(감지 · 충돌의 읽기 패스)는 parallelFor 로 Worker 와 나눈다. 결과는 엔티티마다
   자기 칸에 쓰고, 컴포넌트에 쓰는 것은 호출 스레드가 순서대로 한다. 레지스트리에 쓰는 일은 병렬 구간에서 하지 않는다
   (ai.behavior 의 그래프 캐시도 수집 단계에서 채운다).
```

## 근거

```text
- tick() 호출은 재생과 기록에서 1:1 이다 — 일시정지·Step·속도 변경이 모두 명령이라 재생에서도 같은 호출 순서가 나온다.
  틱 번호 + editSequence 로 위치를 정하면 "어느 호출에서 큐에 넣을지" 를 따로 재구성해야 한다.
- saveId 는 ADR-0015 에서 이미 엔티티 참조의 저장 형식이다. 같은 호출에서 만든 엔티티를 같은 호출의 명령이 가리키는
  경우는 없다 — 명령을 내는 쪽은 생성 결과(netId)를 다음 틱에야 받는다.
- JSON Lines 는 사람이 읽고 diff 하기 쉽고, 손으로 고친 리플레이로 불일치 진단을 시험할 수 있다 (단위 테스트가 그렇게 한다).
  크기는 eco_lifecycle 600틱에 명령 492개 · 500줄 수준이다.
- 읽기 전용 패스는 결과가 조각 수와 무관하다 → D5 가 그대로 성립한다 (CTest 가 --threads 0,1,8 로 확인).
  2코어 클라우드 컨테이너에서 ecosystem_10k 평균 10.4 → 7.6 ms (Worker 1).
```

## 결과

- 얻는 것: 일시정지 편집을 포함한 D3 가 네 시나리오에서 성립. Worker 가 있으면 감지·충돌 비용이 줄어든다.
- 포기하는 것: 리플레이 파일이 바이너리보다 크다 (Phase 9 전까지). 읽기 전용 패스 하나마다 결과 배열 하나를 더 쓴다.
- 위험: 병렬 구간에서 실수로 레지스트리에 쓰면 데이터 경합 → D5 테스트(--threads 0,1,8)와 코드 리뷰로 막는다.
  재생 대상 해석은 enqueue 시점이다 — 같은 호출 안의 생성 결과를 가리키는 명령을 넣는 도구가 생기면 다시 본다.

## 대안

| 대안                                                     | 기각 사유                                                                              |
|----------------------------------------------------------|----------------------------------------------------------------------------------------|
| (tick, editSequence) 로 위치                             | 미리 큐에 넣으면 실행 틱과 편집 단계 몫이 섞인다. 호출 단위 재구성이 더 복잡하다       |
| netId 를 그대로 기록                                     | 세이브에서 시작하는 재생에서 다른 엔티티를 가리킨다                                    |
| 바이너리 형식부터                                        | 명령 코덱이 와이어 포맷과 두 번 만들어진다                                             |
| 감지 결과를 여러 틱에 나눠 갱신 (엔티티마다 N틱에 한 번) | 결과가 틱을 넘어 남는 상태가 된다 → 저장·해시해야 한다 (ADR-0015 의 틱 캐시 규칙 위반) |
