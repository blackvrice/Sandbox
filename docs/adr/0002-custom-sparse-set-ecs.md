# ADR-0002. 자체 Sparse Set ECS를 쓴다

- 상태: **Accepted** · 날짜: 2026-10-05
- 반전: RTS ADR-0003 ("조합은 쓰되 전면 ECS로 가지 않는다")
- 관련: [02-ECS](../02-ECS.md)

## 맥락

RTS ADR-0003은 "한 판에 수백 규모라 ECS의 캐시 지역성 이득이 없다"를 근거로 ECS를 기각했습니다.
이 프로젝트의 목표는 **50,000 엔티티**이고, 에디터에서 사용자가 컴포넌트를 수시로 붙이고 뗍니다.
요구사항은 Custom ECS이며, 처음부터 Archetype을 만들지 말라고 명시합니다.

## 결정

Generation EntityId(64비트) + 페이지형 Sparse Set + Dense 배열(T 단위 AoS) + 틱 단위 변경 추적 + 리플렉션 Visitor.
구조 변경은 EntityCommandBuffer로만.

## 근거

```text
1. 규모 전제가 바뀌었다 (수백 → 5만). ADR-0003 근거 1 소멸.
2. Sparse set 은 컴포넌트 추가/제거가 O(1) 이고 다른 컴포넌트를 옮기지 않는다 — 에디터 사용 패턴에 맞다.
3. 변경 추적(changed[] 틱)이 저장소에 내장되면 복제·증분 저장·Inspector 가 같은 정보를 쓴다.
4. 리플렉션 하나로 Save/Network/Hash/Inspector 를 만들어 RTS 의 "해시에 빠진 필드"(H3) 문제를 구조로 막는다.
```

## 결과

- 얻는 것: O(1) 구조 변경, 단순한 구현, 자동 dirty 추적, 결정론 보조(정렬 순회 규칙).
- 포기하는 것: 다중 컴포넌트 순회에서 Archetype 수준의 지역성.
- 위험: 50k에서 다중 컴포넌트 view가 병목 → 14-PERFORMANCE 6장 조건에서 group/archetype 검토.

## 대안

| 대안                           | 기각 사유                                      |
|--------------------------------|------------------------------------------------|
| EnTT                           | 요구사항이 Custom ECS. 단 벤치 기준선으로 사용 |
| Archetype (flecs 방식)         | 측정 전 복잡도. 잦은 구조 변경 비용            |
| RTS식 조합(std::optional 멤버) | 5만 규모와 데이터 주도 컴포넌트 구성에 부적합  |

## 재검토 조건

자체 구현이 같은 시나리오에서 EnTT 대비 2배 이상 느리고 원인을 줄이지 못할 때.
