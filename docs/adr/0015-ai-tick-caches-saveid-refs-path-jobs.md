# ADR-0015. 행동 상태는 saveId 로 참조하고, 틱 캐시는 저장하지 않으며, 경로 Job 은 다음 틱에 제출 순서로 받는다

- 상태: **Accepted** · 날짜: 2026-10-05
- 관련: [03-SIMULATION](../03-SIMULATION.md) 0장·5~7장, [02-ECS](../02-ECS.md) C2·14장, [04-DETERMINISM](../04-DETERMINISM.md) D2·D5·7장,
  [11-CONTENT-SCHEMA](../11-CONTENT-SCHEMA.md) 0장 (Phase 5B)

## 맥락

Phase 5B 에서 감지·FSM·상호작용·경로·충돌을 넣었다. 결정론(D1·D2·D5)을 지키면서 정해야 할 것이 다섯 가지였다.

```text
1. 행동의 대상(seek 가 고른 먹이)을 컴포넌트에 남겨야 한다. EntityId 는 세이브·로드 뒤 달라진다 (Hint::EntityRef 의
   saveId 변환은 아직 없다).
2. 감지 결과·이번 틱의 interact 같은 값은 매 틱 다시 계산된다. 저장·해시할지?
3. 문서의 ai.sensor 는 태그 마스크(TagSet)를 든다 → 컴포넌트 안에 태그 비트가 생기면 세이브 로드 때 태그 표 재매핑
   대상이 늘어난다(ADR-0014 2번). 무엇을 감지할지는 이미 Behavior 그래프에 적혀 있다.
4. 경로 Job 은 Worker 에서 돈다. 결과가 Worker 수·완료 순서와 무관해야 하고(D5), 진행 중에 저장해도 같은 미래여야 한다(D2).
5. 문서의 ai.path_request(요청) · ai.path_follow(경로)는 붙였다 뗐다 하는 두 컴포넌트다 — 매 요청이 구조 변경이 된다.
```

## 결정

```text
1. 엔티티 참조는 saveId(u64) 필드로 둔다 (ai.behavior.target). SimulationWorld 가 saveId → EntityId 조회표(SaveIndex)를
   정체성 장부와 함께 맞추고 SystemContext.saves 로 준다. 순회하지 않는 조회 전용 표다 (04 4.2).
2. "틱 캐시" = 그 틱 안에서 읽기 전에 반드시 다시 쓰는 값. reflect 에 넣지 않는다 → 저장·해시·복제되지 않는다.
   ai.sensor.sensed (Stage 6 가 쓰고 7 이 읽음), ai.behavior.pendingAction (7 → 10), ai.behavior.cacheIndex (그래프 인덱스).
   포인터는 두지 않는다 (02 C2) — 그래프 캐시도 인덱스 + id 확인.
3. ai.sensor 는 radius 만. 로더가 그래프의 sensed · seek · flee 의 서로 다른 TagExpr 를 질의로 모아 번호를 매기고(최대 8),
   SensorSystem 은 질의마다 개수와 가장 가까운 개체(거리², 동점 saveId)를 낸다.
4. 경로 Job 계약 (03 7.1): Stage 8 이 saveId 순으로 예산만큼 제출 — Job 은 (시작, 목표, 확장 상한)과 불변 PathGridSnapshot 을
   값으로 붙잡고 자기 칸에만 쓴다. 다음 틱 Stage 5 가 **모두 기다린 뒤 제출 순서로** 적용한다. Worker 풀은
   foundation/job/JobSystem (Worker 0 = 그 자리에서 계산 — D5 의 기준). 진행 중인 Job 은 저장하지 않는다:
   ai.path 가 Submitted 와 시작 위치(start)를 들고 저장되고, 로드가 끝날 때 같은 입력·같은 지형(다음 틱 명령 전)으로
   다시 제출한다.
5. ai.path 하나: 상태 None · Pending · Submitted · Following · Failed + goal · start · waypoints(≤16) · cursor · partial.
   요청은 상태만 바꾼다 (구조 변경 없음). 이동 목표가 1 이상 바뀌고 직선이 막혔을 때만 요청한다.
```

## 근거

```text
- saveId 는 이미 세이브의 정체성이고 해시 순서의 기준이다. 필드 하나로 저장·해시·로드가 그대로 맞는다.
  EntityRef 자동 변환은 복제(netId)와 같이 설계하는 편이 낫다 (Phase 10).
- 틱 캐시를 저장하면 세이브가 커지고, 해시에 넣으면 "계산 순서상 아직 안 쓴 값"이 해시를 흔든다. 읽기 전에 항상 다시
  쓰는 값이면 로드 직후 첫 틱에도 같은 값이 된다 — D2 를 깨지 않는다 (eco_lifecycle 의 여러 저장 시점으로 확인).
- 질의를 그래프에서 끌어오면 Prefab 작성자가 같은 태그를 두 곳(마스크·그래프)에 맞춰 쓸 일이 없다.
- 결과 적용 틱과 순서를 고정하면 Worker 쪽은 아무 순서로 끝나도 된다. 로드 후 재계산은 입력이 같고 A* 가 순수
  함수라 같은 결과다 — 진행 중 Job 을 직렬화하는 것보다 단순하다.
- 구조 변경 없는 상태 전이는 ECB·SpawnQueue 와 엮이지 않고, 같은 틱에 바로 보인다.
```

## 결과

- 얻는 것: 행동·경로가 세이브 왕복(D2)과 Worker 수(D5)에 대해 결정적이다. Clang 19 · GCC 13 같은 해시.
- 포기하는 것: 대상이 saveId 라 쓸 때마다 조회(해시 표) 한 번. 감지는 질의마다 "가장 가까운 하나"와 개수만 —
  "두 번째로 가까운" 같은 질의는 노드를 더해야 한다. 경로는 요청 다음 틱에야 따라가기 시작한다(그동안은 곧장 간다).
- 위험: 틱 캐시 필드에 실수로 "다음 틱까지 남는 값"을 넣으면 D2 가 깨진다 → 02 에 규칙을 적었고 D2 테스트(진행 중 Job
  저장 포함)가 잡는다. 경로 예산(틱당 64)을 넘는 요청은 다음 틱으로 밀린다 — 10k 에서의 대기열은 5C 에서 잰다.

## 대안

| 대안                                                 | 기각 사유                                                                                                                  |
|------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| target 을 EntityId + Hint::EntityRef                 | 로드 후 다른 엔티티를 가리킨다. 자동 변환은 아직 없다                                                                      |
| 감지 결과를 저장·해시                                | 세이브가 커지고, 다음 틱에 다시 계산되는 값이라 얻는 것이 없다                                                             |
| 진행 중 Job 의 결과를 세이브에 기록                  | 저장이 Job 완료를 기다려야 하고 형식이 늘어난다. 재계산이 같은 결과를 낸다                                                 |
| 완료된 Job 부터 적용                                 | 완료 순서가 스레드 스케줄에 달려 D5 가 깨진다                                                                              |
| PathGridSnapshot 청크 블록 copy-on-write (문서 초안) | 지금 크기(512²)에서는 전체 배열 복사(256 KB, 지형이 바뀐 틱에만)가 더 단순하고 A* 안쪽 루프가 빠르다. 2048² 에서 다시 본다 |

## 재검토 조건

복제(Phase 10)에서 엔티티 참조를 netId 로 보내야 할 때 (EntityRef 변환과 함께 다시 설계), 10k 생태계에서 경로 예산·감지 비용이
틱 예산을 넘을 때 (5C), System 내부 병렬화(Phase 15)로 틱 캐시를 Job 이 채우게 될 때.
