# ADR-0038. Phase 15 는 결과가 같은 최적화만 — 태그 종류 색인, 자기 엔티티만 쓰는 System 내 병렬, 바이트 템플릿 · 공유

- 상태: **Accepted** · 날짜: 2026-10-19
- 관련: [14-PERFORMANCE](../14-PERFORMANCE.md) 1 · 6 · 7.12장, [04-DETERMINISM](../04-DETERMINISM.md) 7장,
  [05-WORLD](../05-WORLD.md) 4장, [08-NETWORK](../08-NETWORK.md) 6장, [ADR-0016](0016-replay-call-index-json-lines.md),
  [ADR-0025](0025-replication-change-stamp-records-epochs.md), [16-ROADMAP](../16-ROADMAP.md) Phase 15

## 맥락

Phase 15 = 측정 기반 최적화 (14 6장의 착수 조건을 넘은 것만, 커밋마다 전후 벤치 + 해시 동일). 완료 기준은 50k 에서 평균
tick < 10 ms · p99 < 25 ms. 그런데 50k 생태계 시나리오가 없었다 (10k 만). 측정 (2코어 클라우드, clang Release, Worker 1):
ecosystem_50k 평균 46.6 ms — 감지 20 · 충돌 9.3 · 행동 6.6 · 번식 등 3.6 ms, 색인 재구성 2.2 ms. 스냅숏 만들기 클라 16 ·
화면 25 ms, 월드 전체 219 ms. 정할 것:

```text
1. 50k 기준 시나리오        2. 결과를 바꾸는 최적화(감지 주기 줄이기 등)를 허용하나
3. 감지 · 충돌 · 번식의 이웃 질의   4. 쓰기가 있는 System 의 병렬화 규칙
5. Prefab 생성(JSON)          6. 복제 인코딩    7. 완료 판정을 어느 기계에서
```

## 결정

```text
1. ecosystem_50k: 448 × 448 (14 × 14 청크), 50,000 개체, 1,000 틱 — 10k 와 같은 밀도 · 같은 호수 · 흙 수 (반지름이 지도
   폭에 비례해 비율이 같다). sbx_bench sim.ecosystem 이 10k(3,000 틱)와 50k(예열 30 + 1,000 틱)를 함께 잰다.
2. 15A · 15B 는 결과가 비트 단위로 같은 최적화만 한다 (kSimVersion 그대로, 골든 · 기준 해시 동일). 감지 주기 · 반경 같은
   동작 변경은 밸런스와 함께 따로 (ADR 필요).
3. 공간 색인 (SpatialIndex):
   - 위치 사본(SoA)만 훑고 범위 안 항목만 entries 를 읽는다. 정렬은 u32 순열로.
   - 태그 집합을 재구성마다 "종류" 번호로 묶고(intern), 종류가 32 이하이면 종류마다 고운 격자(4 × 4 타일)의 작은 색인을 둔다
     (위치 · 엔티티 · saveId SoA, 행마다 원의 현 밖 칸은 넉넉한 여유를 두고 건너뜀 — 판정은 항목마다 그대로).
     이 색인의 순서는 S1 이 아니다 → 순서와 무관한 질의(개수 · 최소)만 쓴다.
   - 감지: 그래프마다 "종류 → 일치 질의 비트" 표를 한 번 만들고 일치하는 종류의 색인만 훑는다 (늑대는 풀을 건너뛴다).
   - 충돌: 후보의 콜라이더 · 위치를 레지스트리 대신 이번 틱 항목 표(엔티티 index → 항목)에서. 후보 반경의 상대 반지름은
     이번 틱 항목의 최대 반지름 (상한 2 대신) — 겹칠 수 있는 이웃은 모두 그 안이라 찾는 이웃 · 더하는 순서가 같다.
   - 번식: 이웃의 Prefab 비교를 "엔티티 index → Prefab 번호" 표로 (처음 필요할 때 한 번).
   - 셀 계산 · 지형 이동 비용 조회는 인라인 (floor 호출 · 청크 찾기 없이 — 같은 값).
4. System 내 병렬 (04 7장의 "dense 범위 분할"을 구체화): Worker 가 레지스트리에 써도 되는 조건 =
   (a) 자기 엔티티의 컴포넌트에만 (풀의 원소 칸 — 값 · changed 틱이라 서로 겹치지 않는다),
   (b) 그 System 이 쓰는 컴포넌트를 다른 엔티티에서 읽지 않는다, (c) 구조 변경 · 이벤트 · ECB · 공유 컨테이너 없음,
   (d) 난수는 엔티티 스트림, (e) 공유 캐시 칸(graphOf 의 cacheIndex 같은 것)은 호출 스레드에서 먼저.
   이 조건으로 행동(Stage 7) 평가를 Worker 와 나눈다. 충돌 쓰기 패스의 지형 밀어내기 계산도 나누고 쓰기만 순서대로.
   검증: D5(--threads 0,1,4 같은 해시) + TSan.
5. Prefab 템플릿: 덮어쓰기 없는 생성(번식 · 시나리오 배치)은 처음 한 번 JSON 으로 만든 컴포넌트 값을 BinaryCodec 바이트
   (반사 필드 전부, 비트 그대로)로 기억해 다음부터 읽는다 (위치만 쓴다). contentRevision 이 바뀌면 버린다.
6. 복제 (15B): 한 build 안에서 (엔티티, 컴포넌트) 바이트는 한 번만 인코딩해 클라이언트들이 나눠 쓴다. 관심 엔티티는 collect
   가 만든 청크별 목록에서 모은다. netId 정렬은 기수 정렬, 복제 mask 는 풀마다 한 번 훑어 index 표로. 메시지 바이트 동일.
7. 완료 판정은 사용자 PC (코어가 더 많고 단일 스레드도 빠르다 — 14 7.11 에서 1.6 배) 의 sbx_bench --threads N 으로 한다.
   2코어 클라우드는 전후 비교 · 회귀 감시용.
```

## 근거

```text
- 결과가 같은 최적화만 하면 골든 · 리플레이 · 세이브 호환이 그대로고, 해시 비교 하나로 정확성을 확인한다. 동작을 바꾸는
  최적화는 밸런스 판단이 함께 필요해 성능 작업과 섞지 않는다.
- 비용은 개체 수보다 이웃 수(밀도 × 반경²)를 따른다 (14 7.5). 감지 후보의 84 % 가 풀인데 늑대는 풀을 보지 않는다 —
  종류별 색인이 가장 큰 낭비를 없앤다. 질의 일치를 후보마다가 아니라 종류마다 한 번 계산한다.
- 쓰기가 있는 System 의 병렬화를 "Job 별 ECB → 병합" 으로만 하면 행동처럼 자기 컴포넌트만 바꾸는 System 이 이득 없이
  복잡해진다. 원소 칸 쓰기는 데이터 경쟁이 아니고, 읽기 집합이 쓰기 집합과 겹치지 않으면 순서와 무관하다.
- Prefab 생성은 JSON 파싱 · 검증 · 오류 문장 서식이 대부분이었다 (번식 틱의 최대값, 시나리오 첫 틱 50k 생성 650 ms).
- 복제의 클라이언트별 비용은 같은 개체를 여러 클라이언트가 볼 때 같은 인코딩의 반복이었다 (월드 전체 · 겹치는 화면).
```

## 결과

- 얻는 것 (2코어 클라우드, 같은 기계 번갈아 측정 — 14 7.12): 50k 평균 tick Worker 0 63.7 → 38.5 ms, Worker 1 46.6 → 29.6 ms
  (p99 81 → 53 ms), 10k 9.4 → 5.5 ms (Worker 0). 50k 첫 틱(배치) 650 → 455 ms. 스냅숏 만들기 클라 16 · 월드 전체
  219 → 127 ms, 클라 4 · 월드 전체 64 → 34 ms, 클라 16 · 화면 25 → 20 ms. 해시 · 메시지 바이트 동일.
- 아직 아닌 것: 2코어에서 50k < 10 ms 는 못 맞췄다 — 판정은 사용자 PC 측정을 기다린다 (16 Phase 15). 스냅숏 클라 16 <
  3 ms 도 아니다 — 메시지 구조(컴포넌트마다 vector)와 클라이언트별 결정 · 기록이 남는다.
- 포기하는 것 / [계획]: 색인 증분 갱신 (재구성 ≈ 2 ms — 조건 충족이지만 tick 의 7 %, 증분의 복잡도에 비해 작다), 감지의
  원 안 칸 합산(요약 표), 시스템 간 병렬(AccessSet), 번식 · 이동 단계의 병렬, 스냅숏 Net 스레드 · 메시지 아레나, 위치 양자화.
- 위험: 종류별 색인 순서가 S1 이 아니다 — 순서에 기대는 질의가 그것을 쓰면 결정론이 깨진다 (API 주석 · 이 ADR).
  Worker 쓰기 규칙을 어기는 행동(구조 변경 · 이벤트)이 생기면 행동 병렬을 다시 나눠야 한다 (BehaviorSystem 주석).

## 대안

| 대안                                     | 기각 사유                                                                       |
|------------------------------------------|---------------------------------------------------------------------------------|
| 감지를 엔티티마다 N 틱에 한 번 (분산)    | 동작이 바뀐다 (반응 지연 · 해시) — 밸런스와 함께 따로                           |
| 행동 병렬을 Job 별 결과 버퍼 → 순서 적용 | 쓰기 대상이 자기 컴포넌트뿐이라 버퍼 · 복사만 늘어난다                          |
| 색인 증분 갱신                           | 50k 재구성 2 ms (tick 의 7 %) — 개체마다 이전 칸 추적 · 삭제의 복잡도가 더 크다 |
| 시스템 간 병렬 스케줄러                  | AccessSet 선언 · 웨이브 · ECB 병합이 필요 — System 내 병렬이 먼저 남은 몫을 줄였다 |
| Prefab 값을 C++ 템플릿 객체로 복사       | 카탈로그가 타입을 모른다 (복사 함수 없음) — 바이트 형식은 이미 있다               |

## 재검토 조건

사용자 PC 에서 50k 평균 > 10 ms 이면 (남은 직렬 몫: 번식 · 재구성 · 이동 · 충돌 모으기 순으로), 태그 종류가 32 를 넘는
콘텐츠가 생기면 (종류별 색인이 꺼진다), 클라이언트 16 이상을 실제로 받을 때 (스냅숏을 Net 스레드로).
