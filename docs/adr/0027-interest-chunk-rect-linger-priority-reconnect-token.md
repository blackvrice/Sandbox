# ADR-0027. 관심 영역은 청크 사각형 구독 + 빠진 청크의 지연 해제로, 예산 순서는 spawn 먼저 · 거리 · 미룬 시간으로, 다시 접속은 세션 토큰으로 한다

- 상태: **Accepted** · 날짜: 2026-10-08
- 관련: [08-NETWORK](../08-NETWORK.md) 4 · 5 · 6.3 · 8장, [14-PERFORMANCE](../14-PERFORMANCE.md) 1.4 · 7.11,
  [ADR-0025](0025-replication-change-stamp-records-epochs.md), [ADR-0026](0026-network-session-local-server-inspect.md),
  [16-ROADMAP](../16-ROADMAP.md) Phase 11

## 맥락

Phase 10 까지는 모든 엔티티를 모든 클라이언트에 보냈다. 50k 월드면 클라이언트당 스냅숏이 1 MB (14 MB/s) — 256 KB/s
예산에서는 화면에 보이는 개체조차 늦게 온다. Phase 11: 11.1 Subscribe · 관련 청크/엔티티 · alwaysRelevant, 11.2 히스테리시스 ·
우선순위 · 예산, 11.3 지형 캐시 · Late Join, 11.4 Reconnect 토큰. 완료 기준: 50k 에서 클라이언트당 바이트 ∝ 가시 엔티티,
Late Join < 2 초. 정할 것:

```text
1. 구독 형식 — 08 8장 원안은 청크 목록 (≤ 256)
2. 히스테리시스 — "구독 해제 2 초 지연" 을 무엇으로 셀까 (서버 시간? 틱? 일시정지 중에도?)
3. 관심 밖으로 나간 엔티티 · 다시 들어온 엔티티
4. 예산 순서 — 10A 는 netId round-robin. 원안: 선택·소유 > 카메라 거리 > 마지막 전송 후 경과
5. 지형 — 관심 청크만? 나간 청크는?
6. 다시 접속 — 토큰 수명, 이미 살아 있는 연결의 토큰, 복제 상태는 이어 갈까
```

## 결정

```text
1. Subscribe (10, C→S, Control) = 청크 사각형 (양끝 포함) 또는 all. 클라이언트는 화면에 보이는 사각형 + 1 청크 여유를
   월드 경계로 잘라 보낸다 (전체가 보이면 all), 바뀔 때만 · 초당 2 번까지. 구독 전 = 월드 전체 (probe · 옛 동작).
   서버도 월드 경계로 자른다. 디코드: 뒤집힌 사각형 · 축마다 128 청크 이상은 형식 오류.
2. 빠진 청크는 interestLingerSnapshots (30 = 15 Hz 에서 2 초) 번의 스냅숏 동안 관심에 남는다 — 스냅숏 수로 세므로
   일시정지 중에도 · 시험에서도 결정적이다. 월드 전체 → 사각형은 남기지 않는다.
3. 관심 = 관심 청크 안의 엔티티 + 늘 보낼 것(선택한 개체 = Inspect 집합, 위치 없는 개체). 관심 밖 = 지금 없는 것과
   같아 ADR-0025 의 despawn 규칙이 그대로 지운다, 다시 들어오면 spawn. 청크는 core.transform 위치로 (스냅숏마다).
4. 예산이 있으면 우선순위 정렬: 늘 보낼 것 → spawn(처음 보는 개체) → update, 같은 단계 안에서는 관심 중심 거리 −
   미룬 틱 × 0.5 칸. 미룬 시각은 클라이언트별로 기억 (보내면 지운다). round-robin 커서는 없앤다.
5. 지형: 관심 청크 중 이 클라이언트에 보낸 revision 과 다른 것만, 중심에서 가까운 것부터 스냅숏당 64. 관심에서 빠진
   청크는 클라이언트가 들고 있다 (돌아왔을 때 revision 이 같으면 다시 안 보낸다). 바뀐 청크는 관심에 들어올 때 보낸다.
6. 다시 접속: Welcome.sessionToken(16 바이트)을 Auth.token 으로. 서버 표 = 토큰 → {clientId, 역할}. 끊기면 60 초
   (reconnectSeconds) 유효, 스스로 나가면(ClientQuit) 지운다. 살아 있는 연결의 토큰이면 옛 연결을 Kicked 로 끊고 이어
   받는다. 같은 clientId · 역할 · 토큰, 복제는 처음부터 (새 ClientWorld · epoch). 클라이언트(NetworkSession)는 시간 초과로
   끊기면 2 초마다 같은 토큰으로 다시, 60 초 넘으면 실패 — 그동안 옛 복제본을 그리고, 새 연결이 첫 스냅숏을 받으면 바꿔 낀다.
   거절 · 서버 종료 · Kicked 는 바로 실패.
```

## 근거

```text
- 카메라 화면은 사각형이다 — 목록보다 짧고(4 정수), 서버는 청크 비트맵 하나로 판정한다 (50k 판정 + 스냅숏 9 ms 중 대부분은
  월드 훑기 — 클라이언트 수와 무관). 256 청크 상한은 쓰지 않는다: 줌 아웃하면 실제로 다 보이고 예산이 양을 정한다.
- 스냅숏 수로 센 지연 해제는 서버 시계 · 속도 배율과 무관하고 Inline 시험에서 정확히 셀 수 있다.
- spawn 우선: 새 접속 · 화면 이동 때 "아무것도 없음" 이 "조금 늦은 위치" 보다 나쁘다. 측정: 50k, 화면 하나(2.3k 개체),
  256 KB/s 에서 거리 순만이면 99 % 받기까지 77 스냅숏(5.1 초) — 가까운 개체의 갱신이 예산을 먹었다. spawn 먼저면 5
  스냅숏(0.33 초). 미룬 시간 가중은 갱신이 끝없이 밀리는 개체(멀리 있는)를 막는다.
- 토큰 표는 Net 절반에만 있다 (월드와 무관). 상태를 이어 가지 않는 이유: 끊긴 동안 ack 기록이 의미 없어 어차피 새 epoch
  이고, 클라이언트 쪽도 새 ClientWorld 가 간단하다 — 대신 옛 복제본을 그려 화면이 비지 않게 한다.
```

## 결과

- 얻는 것 (Release, 2 코어 컨테이너, `sbx_bench --only net.`): 50k random_walk, 클라이언트당 스냅숏 바이트 = 관심 엔티티 ×
  약 19.6 B (월드 전체 980 KB · 화면 49 KB). 새 접속(화면) 0.33 초, 월드 전체 6.1 초 (256 KB/s). 클라이언트 16 명 화면
  스냅숏 만들기 41 ms (훑기 4 ms + 클라이언트당 약 2.3 ms — 예산이 없을 때. 기본 예산이면 보낼 양이 줄어 더 적다).
- 포기하는 것 / [계획]: 14 1.4 의 "클라 16 · 50k < 3 ms" 는 못 맞췄다 — 클라이언트별 인코딩(같은 개체를 여러 클라이언트가
  보면 바이트 재사용)과 Net 스레드로 인코딩 옮기기 [계획 15]. 256 KB/s 로는 화면 안 2k 개체가 매 틱 움직이면 매번 다
  보내지 못한다 (우선순위로 가까운 것 · 오래된 것부터 — 양자화 · 필드 마스크 [계획 15]). 소유 개체(alwaysRelevant)는
  Phase 12 의 소유 개념과 함께. 다시 접속한 뒤 보낸 명령의 결과가 옛 연결의 순번과 겹칠 수 있다 (한 틱 안의 드문 경우).
- 위험: 관심 경계를 오가는 개체는 30 스냅숏 지연이 지나면 despawn/spawn 을 반복한다 (경계에서 멀리 1 청크 여유가 있어
  화면에서는 안 보인다).

## 대안

| 대안                                                       | 기각 사유                                                                              |
|------------------------------------------------------------|----------------------------------------------------------------------------------------|
| 청크 목록 Subscribe (08 원안)                              | 화면은 사각형 — 목록은 길고 판정이 느리다                                              |
| 히스테리시스를 서버 시간(초)으로                           | 일시정지 · 속도 배율 · Inline 시험에서 셈이 흔들린다                                   |
| 거리 순만 (spawn 우선 없음)                                | 50k 화면 새 접속 5.1 초 — 완료 기준(2 초) 실패                                         |
| 다시 접속 때 복제 기록을 이어 간다                         | 끊긴 동안의 ack 를 알 수 없어 결국 새 epoch — 복잡도만 는다                            |
| 토큰 없이 이름으로 다시 접속                               | 남이 같은 이름으로 역할을 가로챌 수 있다                                               |

## 재검토 조건

클라이언트 수가 많아 스냅숏 만들기가 틱 예산을 위협할 때 (바이트 재사용 · Net 스레드 인코딩), Phase 12 의 소유 ·
에디터 선택이 alwaysRelevant 를 넓힐 때, 월드 경계가 64 청크를 넘을 때 (Subscribe 상한), 서버를 다시 시작해도 이어
가야 할 때 (토큰을 세이브에).
