# ADR-0075. 팩 사이 스크립트 import — "@<팩>/<경로>", 정적 링크 (가져오는 팩의 모듈로 컴파일), 컴포넌트 · 시스템은 정의한 팩의 것

- 상태: **Accepted** · 날짜: 2026-10-28
- 관련: [ADR-0058](0058-bytecode-register-machine-typed-registers-verifier.md) (팩 하나 = 프로그램 하나),
  [ADR-0059](0059-script-components-schema-dynamic-pool-name-order-catalog.md) (스크립트 컴포넌트),
  [ADR-0062](0062-script-systems-define-system-stage-16b-pack-id-order.md) (시스템), [ADR-0071](0071-v0-4-package-manager-scope-pack-as-package-single-version-resolution.md)
  8 (Feature Export / Import — 링크 모델은 M4-T1 에서), [19-SANDBOXSCRIPT](../19-SANDBOXSCRIPT.md) 5 · 11 · 14장,
  [18-PLATFORM](../18-PLATFORM.md) 6.4 (v0.4 M4-T1)

## 맥락

v0.3 의 스크립트는 팩 하나가 프로그램 (바이트코드 모듈) 하나이고 import 는 같은 팩의 상대 경로와 SDK ("sandbox") 뿐이다.
v0.4 의 목표 (설치한 Feature 를 다른 게임이 쓴다) 에는 의존 팩이 정의한 컴포넌트 · 함수를 가져다 쓰는 길이 필요하다. 정할 것:
경로 문법, 무엇을 가져올 수 있나 (직접 의존만?), 모듈을 어떻게 잇나 (VM 의 모듈 사이 호출 · 정적 포함), 컴포넌트 · 시스템을
누가 소유하나, IDE (tsc) 가 같은 import 를 푸는 법.

## 결정

```text
1. 경로: import { X } from "@<팩 id>/<scripts 안 경로>" (확장자 없이) → 그 팩의 scripts/<경로>.ts. 팩 안의 상대 경로 · "sandbox"
   규칙은 그대로. 모양이 틀리면 ("@inv" · "@Inv/x" · scripts 밖으로 나가는 "..") S416
2. 가져올 수 있는 팩 = 가져오는 파일의 팩이 pack.json dependencies · requires 에 직접 적은 팩. 이어지는 의존 (game → rpg → inv 의
   inv) 은 game 이 직접 적어야 한다 (S416 "팩 'inv' 는 이 팩의 의존이 아니다"). 의존 팩의 파일 안의 "@" 는 그 팩의 의존으로 본다
3. 정적 링크: 로더가 팩마다 컴파일할 때 의존 팩 (이어지는 의존까지) 의 scripts 를 "@<팩>/scripts/…" 경로로 함께 넣는다. 검사기는
   이 팩의 모듈과 거기서 import 로 닿는 의존 팩의 모듈만 링크한다 (검사 · 코드 생성 — 쓰지 않는 파일은 들어가지 않는다).
   가져온 함수는 이 팩의 바이트코드에 들어간다 (VM 은 그대로 — 모듈 사이 호출 없음). 최상위는 선언 · 상수뿐이라 (19 5장)
   두 팩이 같은 함수를 따로 가져도 뜻이 같다
4. 소유: 의존 팩의 defineComponent 는 타입 · 컴포넌트 표 (id) 에 쓰지만 등록은 정의한 팩이 한다 (한 번 — 로드 순서상 의존이 먼저).
   의존 팩의 defineSystem 은 시스템 표에 넣지 않는다 (그 팩이 돌린다). 의존 팩 모듈의 export 는 이 팩의 export 표에 넣지 않는다
5. 진단: 의존 팩의 파일에서 난 진단은 그 팩을 컴파일할 때 이미 낸다 — 가져오는 팩의 컴파일에서는 버린다 (같은 오류를 두 번 내지
   않는다). 의존 팩에 오류가 있으면 가져오는 팩도 코드를 만들지 않는다 (로드는 어차피 실패한다)
6. IDE: tsconfig.json 의 compilerOptions.paths 에 스크립트가 있는 팩마다 "@<팩>/*" → "<팩 폴더>/scripts/*" (baseUrl ".") 와 설치
   폴더의 include. sbx install · update · add · remove 가 만든 그대로의 tsconfig.json 만 고쳐 쓴다 (사용자가 고친 파일은 둔다).
   sandbox.d.ts 는 바꾸지 않는다 — 다른 팩의 타입은 그 팩의 소스가 tsc 에 준다. 팩이 없으면 v0.3 의 tsconfig 바이트 그대로
```

## 근거

```text
- 정적 링크: VM · 바이트코드 형식 · 검증기 · 세이브 · 복제를 바꾸지 않는다. 모듈 사이 호출 (링크 표 · 다른 모듈의 함수 번호 ·
  연료 회계) 은 v0.4 의 Feature 공유에 필요 없다 — 함수는 순수하고 상태는 컴포넌트 (월드) 에 있다
- 직접 의존만: 이어지는 의존을 몰래 쓰면 중간 팩이 의존을 바꿀 때 깨진다 (npm 의 유령 의존)
- 컴포넌트 · 시스템 소유: 같은 id 를 두 번 등록하면 겹침 (V1), 시스템을 두 번 돌리면 효과가 두 배다. 정의한 팩 하나가 갖는다
- 쓰는 파일만 링크: 의존 팩이 커도 가져오는 쪽 모듈 · 컴파일 시간은 쓰는 만큼
```

## 결과

- 얻는 것: 설치한 Feature 팩의 컴포넌트 · 함수를 게임 팩의 스크립트가 "@inv/mana" 로 쓴다. 엔진 실행 경로는 그대로.
- 포기하는 것: 모듈 사이 공유 상태 (없다 — 최상위 변수가 없다), 의존 팩의 함수를 고치면 가져오는 팩도 다시 컴파일해야 하는 것
  (로드가 매번 컴파일하므로 저절로 된다), 바이트코드 크기 (같은 함수가 팩마다 들어간다 — 쓰는 것만).
- 위험: 의존 팩의 스크립트 오류가 가져오는 팩의 "코드를 만들지 않는다" 로 이어진다 (진단은 의존 팩의 것 하나). 가져오는 팩이
  의존 팩의 컴포넌트를 쓰려면 그 팩이 로드되어야 한다 — requires 가 로드 순서를 정하므로 늘 그렇다.

## 대안

| 대안                                        | 기각 사유                                                                     |
|---------------------------------------------|-------------------------------------------------------------------------------|
| VM 의 모듈 사이 호출 (동적 링크)            | 바이트코드 · 검증기 · 연료 · 트랩 보고를 모두 바꾼다 — v0.4 가 필요로 하지 않는다 |
| 이어지는 의존도 가져오기                    | 유령 의존 — 중간 팩이 바뀌면 깨진다                                           |
| 경로 "inv/mana" · "../../inv/scripts/mana"  | 팩 안 상대 경로와 헷갈리고 설치 위치 (content/ · .sandbox/packages) 에 묶인다  |
| 의존 팩의 시스템도 가져오는 팩에 넣기        | 시스템이 두 번 돈다                                                           |

## 재검토 조건

팩 사이에 상태를 나누는 모듈 변수 · 서비스가 필요해질 때 (동적 링크), 바이트코드 크기가 문제일 때, 레지스트리 (v0.6) 의 패키지가
타입 선언 (.d.ts) 만 따로 내려 할 때.
