# ADR-0133. 스크립트 재생 디버그 세션 — 디버그 스레드에서 재생, 멈춘 동안의 요청은 그 스레드로, 어댑터의 모듈 사본

- 상태: **Accepted** · 날짜: 2026-11-12
- 관련: [ADR-0132](0132-script-debugger-brk-patch-local-names-format-12.md) (VM 쪽 — BRK · Debugger), [27-SCRIPT-IDE](../27-SCRIPT-IDE.md) 6장 (방식 B),
  [04-DETERMINISM](../04-DETERMINISM.md), [09-SERIALIZATION](../09-SERIALIZATION.md) 4장 (리플레이), task-registry ST-06-7 (조각 2)

## 맥락

VM 쪽 (조각 1) 은 BRK 를 만나면 훅을 부르고 돌아오면 이어서 돈다 — 호출은 동기다. "멈춤" 은 훅 안에서 기다리는 것이고, 기다리는 동안 사람이
프레임 · 지역 · 감시를 보고 다음 행동 (계속 · 단계) 을 고른다. 재생은 SimulationWorld::tick() 안에서 스크립트를 부르므로 멈춘 자리는 틱의
중간이다. 완료 기준: 재생 중단 · 같은 해시 (디버거로 재생해도 리플레이의 해시 기록 · 끝 해시가 같다).

## 결정

```text
1. core/script/ScriptDebugSession — (시작 세이브를 로드한 월드, 리플레이) 를 받아 ReplayPlayer 로 call 마다 재생한다. 재생은 디버그 스레드
   하나에서 (std::thread). 멈추면 그 스레드가 훅 (Debugger 의 멈춤 처리) 안에서 조건 변수로 기다린다
2. 스레드 경계: UI 스레드는 VM · 월드를 만지지 않는다. 멈출 때 디버그 스레드가 스냅숏 (프레임 · 지역 · 감시 — 글) 을 만들어 넘기고, 멈춘
   동안의 요청 (감시 식 · 중단점 놓기 · 거두기 · 감시 목록) 은 일 (함수) 로 디버그 스레드에 넘겨 그 스레드가 VM 을 읽고 Debugger 를 고친다
   (UI 는 끝날 때까지 기다린다). Running 중에는 중단점을 바꾸지 않는다 (실행 중의 코드를 고치지 않는다). 상태 Ready → Running ↔ Paused →
   Finished · Failed. resume 은 상태를 곧바로 Running 으로 (wait 가 옛 Paused 를 보지 않게)
3. 결정론: 시뮬레이션은 한 번에 한 스레드 (디버그 스레드) 에서만 돈다 — 04 의 "스레드 완료 순서를 보지 않는다" 그대로. 디버거는 읽기만 (ADR-0132
   7) 이라 재생 결과 = 디버거 없는 재생 (시험이 해시 기록 수 · 끝 해시를 비교한다)
4. 모듈 사본: ScriptSystemAdapter::debugModule(팩) 이 그 팩의 실행자를 사본 위의 Interpreter 로 바꾸고 사본을 준다 (콘텐츠의 모듈 · 다른
   월드는 그대로). 팩마다 vm::Debugger — 중단점 = (팩, 파일, 줄). 서버 시스템이 있는 팩만 (클라이언트 시스템은 재생에서 돌지 않는다 — [계획
   v0.7] 라이브)
5. stopAtTick = 그 틱의 tick() 전에 모든 팩의 Debugger 에 armStep (첫 스크립트 줄에서). 한 팩에서 멈추면 다른 팩의 걸어 둔 단계를 거둔다 (멈춤은 하나)
6. abort = 멈춤을 풀고 더 멈추지 않으며 다음 call 경계에서 그친다 (Finished · aborted). 세션을 없애면 abort → 스레드를 기다린 뒤 BRK 를 모두
   거두고 훅을 뗀다 (월드는 세션보다 오래 산다 — 사본 Interpreter 는 원래 코드로 돈다)
7. logpoint 글은 멈출 때 · 끝날 때 모아 둔다 (UI 는 그 사본을 읽는다)
```

## 근거

```text
- 스레드: 동기 호출 안에서 "멈춘 채 기다리기" 는 다른 실행 맥락이 있어야 한다. 대안 (재실행 — 멈출 때마다 처음부터 그 멈춤 번호까지 다시
  재생) 은 스레드가 없지만 단계마다 재생 전체를 다시 돈다 — 긴 리플레이에서 단계가 느리다
- 요청을 디버그 스레드로: VM · Debugger 를 두 스레드가 만지면 잠금이 실행 루프까지 번진다. 멈춘 동안 그 스레드는 놀고 있으니 일을 시키면 된다
- 어댑터의 사본: 콘텐츠의 ScriptPrograms 는 여러 월드가 함께 쓰는 const — 그것을 고치지 않는다
```

## 결과

- 얻는 것: 리플레이 위의 중단점 · 단계 · 프레임 · 지역 · 감시 · logpoint · 틱으로 멈추기, 같은 해시 시험, Studio 창 (조각 3) 이 쓸 API.
- 포기하는 것: 시스템 · 이벤트 단위로 멈추기 (지금은 틱 · 줄), 멈춘 틱의 월드 보기 (월드는 틱 중간 — 조각 3 에서 읽기 전용으로 검토),
  되감기 (재실행 방식이 필요), 클라이언트 시스템.
- 위험: 세션이 멈춘 채 버려지면 스레드가 남는다 — 소멸자가 abort · join 한다. 디버그 스레드에서 월드를 돌리므로 그 월드를 다른 스레드가 그동안
  읽으면 안 된다 (세션이 Running · Paused 인 동안 — 헤더에 적었다).

## 대안

| 대안 | 기각 사유 |
|------|-----------|
| 재실행 (스레드 없이 멈춤 번호까지 다시 재생) | 단계마다 재생 전체 — 긴 리플레이에서 느리다. 되감기에는 좋다 (재검토) |
| 라이브 서버에서 멈춤 (방식 A) | 다른 플레이어 · 틱 예산과 엉킨다 (27 6장) |
| UI 스레드가 멈춘 VM 을 바로 읽기 | 메모리 가시성을 잠금으로 맞춰야 하고, 중단점 고치기와 실행이 겹칠 수 있다 |

## 재검토 조건

되감기 요구 (재실행 + 체크포인트), 멈춘 틱의 월드 보기, 클라이언트 시스템 라이브 디버그 (v0.7 계획), 여러 세션 동시.
