# ADR-0066. 스크립트 오버레이 — 종류 Script (값 {id, source}, id = 팩.경로), 다시 컴파일하되 컴포넌트 정의는 그대로, 프로토콜 13

- 상태: **Accepted** · 날짜: 2026-10-26
- 관련: [ADR-0030](0030-roles-player-list-content-overlay.md) (월드 오버레이), [ADR-0052](0052-trigger-editor-form-overlay-kind-protocol-11.md)
  (종류 Trigger · 프로토콜 11 — 같은 방식), [ADR-0059](0059-script-components-schema-dynamic-pool-name-order-catalog.md) (콘텐츠마다 카탈로그),
  [ADR-0062](0062-script-systems-define-system-stage-16b-pack-id-order.md) · [ADR-0064](0064-script-budgets-tick-fuel-disable-after-traps-saved-state.md)
  (시스템 · 상태 digest), [10-EDITOR](../10-EDITOR.md) 8장, [08-NETWORK](../08-NETWORK.md), [09-SERIALIZATION](../09-SERIALIZATION.md) 3장,
  [18-PLATFORM](../18-PLATFORM.md) 6.2 (v0.3 M5-T2)

## 맥락

에디터 "콘텐츠" 창은 Prefab · Rule · Behavior · Trigger 를 월드 오버레이 (EditContent 명령 — 서버 권위 · 복제 · 세이브 · 리플레이)
로 고친다. 스크립트는 팩 파일을 고치고 서버를 다시 열어야 바뀐다. 정할 것: 스크립트를 오버레이 항목으로 어떻게 나타내나 (id ·
값 · 세이브 파일 이름), 오버레이 DB 가 스크립트를 어떻게 다시 만드나, 살아 있는 월드에서 무엇을 바꿀 수 있나, 와이어 호환.

## 결정

```text
1. 종류 Script = 4 (와이어 · 리플레이 · 세이브 폴더 "scripts" — overlay/scripts/<id>.json). 프로토콜 12 → 13
2. 항목 = 팩 파일 하나. id = "<팩 id>.<scripts/ 아래 경로의 마디를 '.' 로, .ts 없이>" — 마디는 소문자 · 숫자 · '_' (콘텐츠 id 규칙,
   세이브 파일 이름이 된다): eco + scripts/ai/wander.ts → "eco.ai.wander" (scriptOverlayId · scriptOverlayPath). 규칙 밖의
   파일 (대문자 · '-' · 점) 은 오버레이로 고칠 수 없다 — 팩에서 고친다. 값 = {"id": id, "source": "<소스>"} (16 KiB — 오버레이
   항목 상한 그대로, 큰 파일은 팩에서). 팩에 없는 경로면 새 파일을 더한다, "팩 값으로" (null) 는 팩 파일로 되돌린다
3. 로더: 오버레이에 Script 항목이 있으면 0 단계에서 그 소스를 팩의 파일 목록에 넣고 (바꾸기 · 더하기) 팩을 다시 컴파일한다.
   진단은 팩 파일 자리 ("<팩 폴더>/scripts/a.ts:줄:열") — 다른 콘텐츠 문제와 같이 그 편집을 거절한다. Script 항목이 없으면
   팩 DB 의 바이트코드를 나눈다 (지금과 같다)
4. 컴포넌트 정의 (defineComponent) 는 바꿀 수 없다: 다시 컴파일한 정의 전부의 지문 (정의 자리 빼고) · id 목록이 팩 DB 와 다르면
   V11 — 살아 있는 월드의 풀 · 카탈로그가 그 모양이다. 카탈로그는 팩 DB 의 것을 그대로 나눈다 (월드 · 클라이언트가 같은 객체를
   본다). 컴포넌트를 바꾸려면 팩을 고치고 월드를 다시 연다 (세이브는 version 으로 옮긴다 — ADR-0061)
5. 월드: 콘텐츠의 바이트코드가 바뀌면 (EditContent 는 명령 단계 2) 스크립트 어댑터를 다시 만든다 — 그 틱의 16b 부터 새 코드.
   이어진 트랩 · 꺼짐은 digest 가 같은 팩의 시스템만 옮긴다 (ADR-0064 4 와 같은 규칙 — 고친 팩의 시스템은 새로 시작)
6. 오버레이 지문 (WorldHash) 은 v0.2 의 넷 다음 종류가 비어 있으면 넣지 않는다 — 스크립트 없는 오버레이의 지문 · 세이브 해시가 그대로
7. 에디터: "콘텐츠" 창의 종류 "스크립트" — 팩의 scripts/*.ts (오버레이 id 로 쓸 수 있는 것) + 더한 파일, 소스를 그대로 고친다.
   "검사" = 이 컴퓨터에서 오버레이로 다시 컴파일 (서버와 같은 로더), 오류마다 그 소스 줄을 붙인다 ("12 | <줄>"). "적용" =
   EditContent Script. 이 파일이 정의한 시스템 요약, 새 파일 틀 (시스템 하나)
```

## 근거

```text
- 오버레이 경로를 그대로: 권한 (콘텐츠 역할) · 서버 검증 · 모두에게 복제 · 되돌리기 · 세이브 · 리플레이가 이미 있다 (ADR-0030)
- id = 팩.경로: 다른 종류와 같은 "<팩>.<이름>" 모양이라 isValidContentId · 세이브 파일 이름 · 와이어 상한을 그대로 쓴다
- 파일 단위 · 팩 다시 컴파일: 스크립트는 팩 하나 = 프로그램 하나 (import 그래프) — 한 파일만 바꿔도 팩 전체를 다시 검사해야 맞다
- 컴포넌트 고정: 동적 풀의 배치를 살아 있는 월드에서 바꾸려면 모든 개체의 값을 옮겨야 하고 (마이그레이션), 클라이언트 · 세이브 ·
  복제가 그 순간에 맞춰야 한다. 시스템 코드만 바꾸는 것이 편집 루프의 대부분이다
- 지문의 빈 종류 빼기: 프로토콜 · 종류를 더할 때마다 옛 세이브의 해시 비교가 깨지지 않게
```

## 결과

- 얻는 것: 게임을 멈추지 않고 스크립트 시스템을 고친다 (모든 접속자 · 세이브 · 리플레이에 같게), 오류가 그 줄과 함께 나온다.
- 포기하는 것: 오버레이로 컴포넌트 정의 바꾸기 · 지우기, 16 KiB 를 넘는 파일, 규칙 밖 이름의 파일, 소스 편집기의 구문 색 · 줄 번호
  (ImGui 글 상자 — [검토 v0.5]).
- 위험: 편집마다 팩 전체를 다시 컴파일한다 (서버 · 클라이언트) — 팩 스크립트가 크면 명령 단계가 길어진다. 측정은 M6 벤치.
  프로토콜 13 — 옛 클라이언트는 접속하지 못한다 (버전 검사가 거절).

## 대안

| 대안                                         | 기각 사유                                                                  |
|----------------------------------------------|----------------------------------------------------------------------------|
| 스크립트 편집을 파일로 쓰고 서버 다시 시작   | 접속자가 끊기고 월드가 처음부터 — 편집 루프가 느리다                       |
| id = 원래 경로 ("eco/scripts/a.ts")          | 세이브 파일 이름 · 콘텐츠 id 규칙에 맞지 않다 (Windows 에서 쓸 수 없는 글자) |
| 오버레이로 컴포넌트도 바꾸기                 | 살아 있는 풀의 배치 변경 · 마이그레이션 · 복제 동기화가 필요하다            |
| 바뀐 파일만 다시 컴파일                       | import 그래프 · 함수 번호가 팩 하나에 걸쳐 있다 (모듈 하나 — ADR-0058)      |
| 지문에 모든 종류를 늘                          | 종류를 더할 때마다 옛 세이브의 해시 비교가 실패한다                        |

## 재검토 조건

에디터가 컴포넌트 정의를 고치는 길을 원할 때 (월드 다시 열기와 함께), 스크립트가 16 KiB 를 넘는 일이 흔할 때 (오버레이 항목 상한 ·
명령 크기), 다시 컴파일 시간이 측정으로 문제일 때.
