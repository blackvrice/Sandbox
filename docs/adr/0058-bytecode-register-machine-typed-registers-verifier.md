# ADR-0058. SandboxScript 바이트코드 — 레지스터 기계, 레지스터마다 타입, 8 바이트 칸, 구조체는 필드 이름 순, 선형 검증기

- 상태: **Accepted** · 날짜: 2026-10-21
- 관련: [ADR-0056](0056-sandboxscript-language-subset-own-compiler-no-gc.md) (언어 · "타입 있는 IR → .sbc → 검증기 → VM"),
  [ADR-0057](0057-host-api-single-definition-cpp-table-sdk-generated.md) (Host 표 · 지문), [19-SANDBOXSCRIPT](../19-SANDBOXSCRIPT.md) 12장,
  [18-PLATFORM](../18-PLATFORM.md) 6.2 (v0.3 M1-T3)

## 맥락

검사기 (M1-T2) 가 타입 · 참조 · 상수값이 정해진 나무 (Program) 를 낸다. VM (M2) 이 돌릴 형식이 필요하다. 바이트코드는 패키지 ·
캐시 · 시험 자료로 파일이 될 수 있고, 그 파일은 믿지 않는다 — 검증기가 VM 의 메모리 안전을 책임진다 (초안 04 5 · 9장 "불법 바이트코드 ·
핸들 위조는 VM 경계에서 거부"). 정할 것: 기계 모양 (스택 · 레지스터), 값 표현, 타입 정보를 어디에 두나, 검증의 범위, 따로 된 IR 층.

## 결정

```text
1. 레지스터 기계. 함수마다 레지스터 표 (≤ 4096) 와 명령열. 명령 = 8 바이트 고정 {op u8, 0, a u16, b u16, c u16} —
   점프 대상 · 32 비트 즉시값은 b | c << 16. 매개변수는 레지스터 0 … n-1, 호출 인자는 연속 레지스터 (c … c+n-1)
2. 레지스터마다 타입 (모듈의 타입 표 번호). 타입 종류: Void · I32 · F64 · Bool · String · Opaque(abi) · Array(원소) ·
   Box(안쪽) · Struct(필드). enum = I32, T | null = (T 가 참조면) T 자신 · (기본 · 불투명이면) Box(T). 모든 레지스터는 프레임
   시작에 0 (null · false · 0) — "초기화 안 됨" 이 없어 검증이 흐름 분석 없이 한 번 훑기다
3. 값은 8 바이트 칸 하나 (i32 · f64 비트 · bool · 참조 · 불투명 핸들). 배열 원소 · 구조체 필드도 칸 — 읽기 · 쓰기 명령은
   타입마다 나누지 않는다 (검증기가 타입을 안다). 산술 · 비교 · 변환 · 문자열화처럼 뜻이 다른 것만 타입별 명령 (ADDI · ADDF …)
4. 구조체 배치 = 필드 이름 (바이트) 순. 같은 필드 이름 집합 + 같은 필드 타입 = 같은 배치 → 구조적으로 같은 두 타입 (interface 와
   익명 객체 타입) 이 같은 객체를 가리켜도 칸이 맞는다. 그래서 검사기는 구조체 필드를 양쪽으로 맞춘다 (readonly 도 — 한쪽 넓힘
   i32 → number 은 칸 표현이 달라 막는다). 검증기의 "같은 타입" 은 구조적 (재귀 구조체는 비교 중인 짝을 가정)
5. 검증기 (선형, 함수마다): 모든 피연산자 레지스터 · 상수 · 함수 · import · 필드 · 점프 대상 번호가 범위 안, 명령마다 피연산자
   타입 규칙, 호출 인자 · 결과 타입 = 서명, 마지막 명령은 끝 (RET · RETV · JMP · TRAP), import 는 Host 표에 같은 id · 같은 서명으로
   있어야 한다, 머리의 Host 표 지문 · 버전 · 형식 번호가 이 엔진과 같아야 한다 (다르면 VersionMismatch — 패키지의 소스에서 다시
   컴파일). 실행 중 확인은 VM 이 한다: null 참조 · 범위 밖 첨자 · i32 % 0 · 연료 · 스택 (트랩 — ADR-0056 5)
6. 따로 된 IR 층은 없다 — "타입 있는 IR" = 검사기의 Program (타입 · 참조 · 상수가 붙은 AST). 상수 접기는 검사기가 했다.
   최적화 (공통 식 · 죽은 코드) 가 필요해지면 그때 IR 층을 넣는다 [재검토]
7. 모듈 = 팩 하나 (모든 스크립트 파일을 한 모듈로 잇는다 — 함수 번호가 전역). export 표 = (파일 경로, 이름) → 함수
8. 파일 .sbc: 머리 "SBXC" · 형식 1 · hostApiVersion · 지문, 그다음 타입 · 문자열 · 수 · import · 함수 · export 표를 길이와 함께
   (리틀 엔디안, 개수 상한). 체크섬은 없다 — 무결성은 패키지의 SHA-256 (ADR-0054), 안전은 검증기
```

## 근거

```text
- 레지스터 기계: 같은 일을 스택 기계보다 적은 명령으로 (인터프리터 비용은 명령 수에 비례), 검사기가 이미 식마다 타입을 알아 레지스터
  배정이 쉽다. 초안 04 5장도 레지스터 VM
- 레지스터마다 타입 + 0 초기화: 검증이 흐름 분석 없는 선형 훑기 — 검증기가 작으면 틀릴 곳이 적다 (믿지 않는 입력의 첫 관문)
- 8 바이트 칸: 배열 · 필드 · 상자 명령이 타입마다 갈리지 않는다. 메모리 안전은 칸 해석을 검증기의 타입이 정하는 것으로 —
  참조 칸에 i32 를 쓰는 바이트코드는 검증에서 막힌다
- 이름 순 배치: 구조적 타입 (TS) 과 참조 의미를 같이 지키는 가장 단순한 길. 배치마다 변환 복사를 하면 별칭 (같은 객체를 두 이름으로)
  이 깨진다
- 체크섬 없음: 파일이 망가졌는지가 아니라 "이 바이트열이 안전한가" 를 검증기가 본다 — 바이트 뒤집기 시험이 검증기를 직접 친다
```

## 결과

- 얻는 것: 작은 선형 검증기, 타입마다 갈리지 않는 메모리 명령, 구조적 타입과 참조의 공존, 소스에서 다시 만들 수 있는 캐시 형식.
- 포기하는 것: 칸이 8 바이트라 i32 · bool 배열이 커진다 (4 · 8 배), 흐름에 따른 레지스터 타입 (같은 레지스터를 다른 타입으로 다시 쓰기).
- 위험: 레지스터 수 (함수가 크면) — 완화: 임시 레지스터를 문장마다 타입별로 돌려 쓴다, 상한 4096 (넘으면 S501).

## 대안

| 대안                                 | 기각 사유                                                                     |
|--------------------------------------|-------------------------------------------------------------------------------|
| 스택 기계                            | 명령이 많다 (인터프리터 비용), 스택 높이 · 타입 검증에 흐름 분석이 필요하다    |
| 레지스터 타입을 흐름으로 추론        | 검증기가 흐름 분석을 한다 — 커지고 틀릴 곳이 생긴다                           |
| 원소 · 필드 타입별 명령 (GETF_I32 …) | 명령 수만 늘고 안전은 같다 (검증기가 타입을 이미 안다)                         |
| 선언 순 배치 + 할당 때 변환 복사     | 같은 객체를 두 타입으로 보면 복사가 별칭을 깬다                                |
| .sbc 에 체크섬                       | 바이트 뒤집기 시험이 체크섬에서 멈춘다 — 안전은 검증기가 보는 것이다           |

## 재검토 조건

v0.3 M6 벤치 (10k 대상) 에서 명령 해석 비용이 틱 예산의 상당 부분이면 (명령 융합 · 상수 피연산자), i32 배열 메모리가 문제가 되면
(원소 종류별 압축 배열), 최적화가 필요해지면 (따로 된 IR 층).
