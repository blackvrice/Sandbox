# ADR-0070. 스크립트 보호 시험 — 나쁜 스크립트는 흔적을 남기지 않는다, 바이트코드 변형 퍼즈, 검증기의 엔진 이름공간 거절, script.regen 벤치

- 상태: **Accepted** · 날짜: 2026-10-27
- 관련: [ADR-0056](0056-sandboxscript-language-subset-own-compiler-no-gc.md) 5 (격리), [ADR-0058](0058-bytecode-register-machine-typed-registers-verifier.md)
  (검증기), [ADR-0060](0060-script-component-host-read-query-write-buffer-entity-handles.md) (핸들 · 쓰기 버퍼),
  [ADR-0064](0064-script-budgets-tick-fuel-disable-after-traps-saved-state.md) (예산 · 트랩 정책), [ADR-0068](0068-script-profile-injected-diagnostic-clock-serverstats-protocol-14.md)
  (진단 시계), [ADR-0069](0069-script-demo-mana-regen-sample-e2e-split-m6.md) (M6 를 셋으로), [14-PERFORMANCE](../14-PERFORMANCE.md),
  [18-PLATFORM](../18-PLATFORM.md) 6.2 (v0.3 M6-T2)

## 맥락

v0.3 완료 기준의 "실행량 초과 · 권한 위반 · 결정론 위반 · VM 크래시 보호" 와 계획의 M6-T2 "보호 시험 (무한 루프 · 권한 위반 · 불법
바이트코드 · 핸들 위조) · 10k 대상 벤치". 부품마다 단위 시험은 있다 (VM 트랩 · 예산 · 트랩 정책 · ctx 위조 · 비트 뒤집기). 정할 것:
"보호된다" 를 무엇으로 판정하나, 어디까지 무작위로 흔드나, 권한의 경계를 몇 겹으로 두나, 스크립트 비용을 무엇으로 재나.

## 결정

```text
1. 판정 = 나쁜 스크립트는 결과에 흔적을 남기지 않는다: 무한 루프 (OutOfFuel) · 무한 재귀 (StackOverflow) · 메모리 폭탄
   (OutOfMemory) 시스템이 쓰기를 먼저 한 뒤 끝나지 않는 콘텐츠의 WorldHash = 그 시스템이 없는 콘텐츠의 WorldHash. 나쁜 시스템은
   호출 3 번 (kDisableAfterTraps) 뒤 꺼지고, 건강한 시스템은 매 틱 그대로. client 시스템의 무한 루프도 그 시스템만 (표시 버림 · 끔).
   실행 파일로도 본다 (SandboxServer --ticks N --exit — 같은 해시, 종료 코드 0)
2. 권한은 세 겹: (a) 검사기 — 도메인 · 주인 타입 (서버 ctx 로 화면 표시 · 클라이언트 ctx 로 쓰기를 부를 수 없다), (b) 검증기 — 모듈의
   컴포넌트 표에 엔진 이름공간 (core · game · …) 이 있으면 거절 (새 규칙 — 검사기는 원래 거절했다, 손으로 고친 모듈이 LOADK 로 엔진
   컴포넌트를 가리키지 못하게), (c) Host — 엔진 컴포넌트 ref 는 HostError (읽기 · 쓰기 모두). .sbc 형식은 그대로
3. 위조: 무작위 개체 핸들 · ctx 2,000 번 (스크립트 함수를 거쳐) 은 모두 HostError · 월드 그대로, 서버 Host 의 ctx · 개체를 클라이언트
   Host 에 넘기면 거절 (표지가 다르다), 무작위 개체 500 번
4. 불법 바이트코드: 직렬화한 모듈을 결정적 의사 난수로 3,000 번 변형 (바이트 1 ~ 4 개 바꾸기 · 잘림 · 한 바이트 끼움) — 읽기 · 검증이
   거절하거나 검증된 모듈, 검증된 것은 기본 타입 매개변수 함수를 모두 작은 연료 (20,000) · 모두 거절하는 Host 로 불러 본다 — 죽지
   않으면 통과. 이 퍼즈가 찾은 검증기 버그 (CALLH 결과가 Entity[] 일 때 없는 결과 레지스터를 범위 확인 전에 읽음) 를 고쳤다.
   CTest 는 3,000 번 (약 1 초), 한 번은 300,000 번 (다른 씨앗) 을 돌려 크래시 0 을 확인했다 (기록)
5. 벤치 script.regen (sbx_bench): 스크립트 컴포넌트를 가진 개체 10,000 (--quick 1,000) 에 서버 시스템 하나가 틱마다 질의 → 읽기 →
   쓰기, 같은 콘텐츠에서 시스템만 뺀 월드와 tick 비교, 진단 시계로 스크립트 단계 ms/틱 · ns/개체 · 연료/개체. 결과는 14 7.13 에
   기록 (머신 · 빌드 · 커밋과 함께)
```

## 근거

```text
- 해시 비교: "죽지 않는다" 만으로는 나쁜 시스템의 쓰기가 새는 것을 못 잡는다. 트랩이면 그 호출의 쓰기를 버린다는 약속 (ADR-0057 5)
  을 끝 결과로 본다
- 무작위 변형 + 실행: 비트 하나 뒤집기는 이미 있었고 버그를 못 찾았다 — 여러 바이트 · 길이 변화가 개수 · 번호 칸을 다른 뜻으로
  만든다. 검증된 변형을 실제로 돌려야 "검증기가 보장한 것을 VM 이 믿는다" 가 시험된다
- 검증기 규칙 하나 더: Host 가 이미 거절하지만, 엔진 컴포넌트를 가리키는 모듈이 검증을 지나면 다른 Host (도구 · 미래 바인딩) 가
  같은 검사를 잊을 수 있다
- 벤치는 최악의 모양 (매 틱 · 모든 개체 · 읽기와 쓰기): 실제 시스템은 주기 (intervalTicks) · 질의 범위로 줄인다
```

## 결과

- 얻는 것: v0.3 완료 기준의 보호 항목이 자동 시험으로 선다. 검증기 버그 하나가 고쳐졌다 (서버가 손상된 바이트코드를 받으면 죽을 수
  있었다 — 지금 콘텐츠 경로는 소스에서 컴파일하므로 실제로 닿지는 않았다).
- 포기하는 것: 퍼즈의 커버리지 측정 (libFuzzer · 계측) — [계획 v0.4 검토].
- 위험: 벤치 결과 (Release, 10,000 개체 · 매 틱 읽기 + 쓰기 ≈ 개체당 약 1 µs) 는 시뮬레이션 예산 (10k 합 10 ms — 14 1.2) 의 대부분이다.
  게임 스크립트는 주기를 두어야 한다 (데모 regen 은 15 틱). Host 경로 (핸들 표 · 쓰기 버퍼의 std::map · 호출마다 바이트 벡터) 의
  최적화는 14 6장의 착수 조건에 따라 [계획].

## 대안

| 대안                                          | 기각 사유                                                                      |
|-----------------------------------------------|--------------------------------------------------------------------------------|
| 죽지 않는지만 본다                            | 트랩난 호출의 쓰기가 새도 통과한다                                             |
| libFuzzer 로 퍼즈                              | MSVC · 기존 CTest 와 따로 돈다 — 결정적 변형 3,000 번으로 회귀를 막고, 깊은 퍼즈는 따로 |
| 엔진 컴포넌트 거절을 Host 에만                | 검증된 모듈이 엔진 컴포넌트를 가리킬 수 있다 — 바인딩마다 같은 검사를 기억해야 한다 |
| 머신 기준선 파일 (bench/baselines/<machine>)  | 이 태스크는 스크립트 한 벤치 — 전체 기준선은 머신마다 전체 실행으로 (14 3장)    |

## 재검토 조건

스크립트를 바이트코드로 배포하게 될 때 (패키지에 .sbc — 검증기가 최전선이 된다: 커버리지 퍼즈), 벤치가 예산을 넘는 게임이 나올 때
(Host 경로 최적화 · 배치 API), 엔진 컴포넌트 쓰기를 열 때 (권한 표와 함께 새 ADR).
