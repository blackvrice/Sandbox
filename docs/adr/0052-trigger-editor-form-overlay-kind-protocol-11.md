# ADR-0052. 트리거 편집 — 오버레이 종류 Trigger (프로토콜 11), "콘텐츠" 창의 표 기반 폼

- 상태: **Accepted** · 날짜: 2026-10-20
- 관련: [ADR-0030](0030-roles-player-list-content-overlay.md) (월드 오버레이 · EditContent), [ADR-0050](0050-visual-trigger-schema-tree-graph-flat-program.md)
  (노드 종류 표), [ADR-0051](0051-trigger-execution-stage-17c-same-tick-cascade-budget.md), [10-EDITOR](../10-EDITOR.md) 8장,
  [08-NETWORK](../08-NETWORK.md) 5장, [09-SERIALIZATION](../09-SERIALIZATION.md) 3장, [18-PLATFORM](../18-PLATFORM.md) 5.1 (M4-T3)

## 맥락

v0.2 M4-T3 "에디터 폼 (노드 목록 · 인스펙터 양식) — 편집은 EditContent 명령 (오버레이 경로)". 트리거는 팩의 triggers/*.json 으로만
쓸 수 있고, 에디터의 "콘텐츠" 창은 Prefab · Rule · Behavior 를 JSON 글자로만 고친다. 정할 것:

```text
1. 트리거를 월드에서 고치는 길 (새 명령 · 기존 오버레이)       2. 와이어 · 세이브 · 리플레이 영향
3. 폼의 모양 (노드 그래프 캔버스 · 목록 양식)                    4. 폼과 JSON 의 관계 · 검사
```

## 결정

```text
1. 기존 오버레이에 종류 하나: ContentKind::Trigger (값 3, 이름 "trigger", 폴더 "triggers"). EditContent{trigger, id, value | null}
   이 팩 트리거를 바꾸거나 더하거나 (null) 뺀다 — 검사 · 적용 · 거절 · 되돌리기 · 전송 · 해시가 Prefab · Rule · Behavior 와 같다.
   바꾼 트리거는 팩의 자리(실행 순서)를 이어받고, 더한 것은 모든 팩 트리거 뒤. 게임 중 (Running) 에도 다음 단계부터 새 콘텐츠
   (트리거는 틱 사이 상태가 없다 — ADR-0051 의 스냅숏 · perTick 은 매 틱 새로).
2. 와이어: EditContent 와 ContentOverlay 메시지의 kind 가 0~3 — 열거 값이 늘었으므로 프로토콜 10 → 11 (메시지 모양 그대로).
   세이브: overlay/triggers/<id>.json (선택 폴더 — worldVersion 1 그대로, overlay/ 의 다른 종류와 같은 근거). 오버레이 지문이
   WorldHash 에 들어가므로 이 폴더를 모르는 옛 엔진은 해시 검증에서 실패한다 (조용히 다르게 돌지 않는다).
   리플레이: {"op": "content", "kind": "trigger", ...} — 명령 JSON 그대로.
3. 폼 = 목록 양식 (editor/ui/TriggerForm): 노드마다 접히는 머리 + id + 표(TriggerSchema)가 정한 키의 위젯 (수 · 정수 · 켜기 ·
   태그 식 all/any/none · 비교 콤보 · 좌표 · 필드 · Prefab 콤보 · 태그 콤보 · 팀 · 결과 콤보 · 이벤트 이름). 선택 키는 "사용"
   상자. 노드 더하기 (종류 콤보 — 필수 키는 기본값, 기본값만으로 검사를 통과한다) · 지우기 (그 노드의 연결도). 연결 = from →
   to 콤보 + else 상자 (조건 노드에서만). 노드 id 를 바꾸면 연결이 따라간다. 이름 · 틱마다(perTick).
   노드 그래프 캔버스 (pos 로 배치 · 끌어 잇기) 는 [계획] — pos · note 는 폼이 건드리지 않고 남긴다.
4. 폼은 원본 JSON 을 바로 고친다 (패널의 text) — "폼" · "JSON" 탭이 같은 글을 본다. 검사 · 적용은 패널의 기존 경로 (이 컴퓨터의
   로더로 V1~V10 → EditContent). 요약에 서버 콘텐츠의 실행 표현 (펼친 명령열) 을 줄로 보인다.
```

## 근거

```text
- 오버레이 재사용: 서버 권위 검사 · 역할 (콘텐츠 권한) · 되돌리기 · 세이브 · 복제 · 해시가 이미 있다. 트리거만의 명령을 두면
  같은 일을 두 번 만든다.
- 목록 양식: 트리거는 나무 (노드 ≤ 64, 깊이 ≤ 16) 라 목록 + 연결 표로 충분하고, 표에서 위젯을 만들어 노드 종류가 늘어도 폼
  코드가 늘지 않는다. 캔버스는 배치 · 끌기 · 확대가 필요해 크고, 실행 의미가 같다.
- 폼 = JSON 의 다른 보기: 같은 글을 고치면 둘이 어긋나지 않고, 폼이 아직 모르는 모양 (모르는 종류 · 깨진 JSON) 은 JSON 탭에서
  고칠 수 있다.
```

## 결과

- 얻는 것: 에디터에서 트리거를 만들고 · 고치고 · 되돌리고 · 저장한다. 게임 중에도 바로 (서버 검사).
- 포기하는 것: 노드 그래프 캔버스, 팩 항목 끄기, 오버레이를 팩으로 내보내기 — [계획].
- 위험: 프로토콜 11 — 10 클라이언트 · 서버와는 접속하지 않는다 (정확 일치).

## 대안

| 대안                                       | 기각 사유                                                                        |
|--------------------------------------------|----------------------------------------------------------------------------------|
| 트리거 전용 명령 (EditTrigger)             | 오버레이 경로 (검사 · 되돌리기 · 세이브 · 복제) 를 다시 만든다                   |
| 노드 그래프 캔버스부터                     | 크다 (배치 · 끌기 · 확대 · 선 그리기), 나무 + 64 노드에는 목록이 읽기 쉽다       |
| 폼이 TriggerDef (컴파일된 것) 를 고친다    | 원본 (pos · note · 순서) 을 잃고 실행 표현 → 원본 되돌리기가 필요하다            |
| 오버레이 kind 를 새 메시지로 (와이어 그대로) | 열거 값 하나에 메시지를 늘리는 것이 더 크다 — 프로토콜 번호로 충분              |

## 재검토 조건

노드 그래프 캔버스가 필요할 때 (노드가 많아지거나 합류 노드가 생기면), 콘텐츠 팩 내보내기가 생길 때 (v0.4 패키지).
