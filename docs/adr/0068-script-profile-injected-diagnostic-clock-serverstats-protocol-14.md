# ADR-0068. 스크립트 프로파일 — 주입한 진단 시계, ServerStats 의 시스템 표 (프로토콜 14), "스크립트 프로파일" 패널

- 상태: **Accepted** · 날짜: 2026-10-27
- 관련: [ADR-0064](0064-script-budgets-tick-fuel-disable-after-traps-saved-state.md) (예산 · 통계), [ADR-0067](0067-client-scripts-domain-client-onupdate-read-only-display.md)
  (클라이언트 스크립트), [ADR-0024](0024-network-foundation-enet-serverhost-two-halves.md) (ServerHost · ServerStats),
  [04-DETERMINISM](../04-DETERMINISM.md), [08-NETWORK](../08-NETWORK.md) 5장, [19-SANDBOXSCRIPT](../19-SANDBOXSCRIPT.md) 22장,
  [18-PLATFORM](../18-PLATFORM.md) 6.2 (v0.3 M5-T4)

## 맥락

스크립트 시스템 통계 (ADR-0064) 는 호출 · 트랩 · 예산 · 연료를 세지만 시간은 없고, 서버 · sbx_sim_check 가 끝날 때 줄로만 보인다.
게임 제작자는 "어느 스크립트가 느린가" 를 게임을 돌리면서 보고 싶다. 정할 것: 시간을 어디서 재나 (시뮬레이션은 벽시계를 보지
않는다 — 04), 서버의 값을 클라이언트에 어떻게 보이나, 무엇을 창 (최근) 으로 · 무엇을 누적으로 보이나.

## 결정

```text
1. 진단 시계는 주입한다: core/script/ScriptClock (u64 (*)() noexcept — 단조 나노초). ScriptSystemAdapter · ClientScriptSystems 의
   setClock, SimulationWorld::setScriptClock (다시 만든 어댑터에도 옮긴다). 엔진 (core) 은 시계를 모르고 부르는 쪽이 넣는다 —
   서버 (ServerHost — 단계마다 그 월드에), 클라이언트 (NetworkSession). sbx_sim_check · 시험 · 리플레이는 넣지 않는다 (끝 줄이
   결정적). 시계가 있으면 호출마다 앞뒤를 재어 통계에만 더한다 (ScriptSystemCounters::nanos · maxNanos, 틱 · 프레임 통계의 nanos)
   — 어떤 분기도 시간을 보지 않는다. 결과 · 해시 · 세이브 · 복제는 시계가 있든 없든 같다 (시험)
2. ServerStats (1 초마다) 끝에 windowSeconds f32 · 스크립트 시스템 표 (실행 순서, 64 줄까지 — 넘으면 scriptsOmitted) — 줄마다
   id (≤ 128 바이트) · 창의 호출 · 연료 · 시간 (앞 통계 뒤의 누적 차이 — 어댑터를 다시 만들어 누적이 줄면 0 부터) · 누적 트랩 · 예산 ·
   건너뜀 · 최대 연료 · 최대 시간 · 꺼짐. 프로토콜 13 → 14. 표는 모든 접속자에게 (역할 무관 — 서버 성능 정보이고 이미 TPS ·
   틱 시간을 보낸다)
3. 클라이언트: IWorldSession::scriptProfile — 서버 표 + client 시스템의 최근 1 초 (실제 시간 창, 같은 누적 차이). 줄 = 호출/초 ·
   연료/호출 · ms/초 · ms/호출 · 최대 ms · 최대 연료 · 트랩 · 예산 · 건너뜀 · 꺼짐 (scriptProfileRow). "스크립트 프로파일" 패널
   (패널이 보일 때만 — 서버 · 클라이언트 표 둘). ADR-0067 의 "스크립트" 칸 아래 통계 접기는 이 패널로 옮긴다 (칸은 print 줄만)
4. 끝 줄: 시계가 있으면 시스템마다 " · 시간 <합> ms · 최대 <호출 하나> ms" (SandboxServer · SandboxClient 헤드리스).
   sbx_net_probe 는 받은 표를 줄마다 찍는다
5. sbx_bench 의 스크립트 단계는 M6-T1 (데모 samples/mana_regen 과 10k 대상 벤치) 로 — 저장소 콘텐츠에 스크립트가 아직 없다
```

## 근거

```text
- 주입: 04 의 "시뮬레이션은 벽시계를 보지 않는다" 를 코드 경계로 지킨다 — core 에는 chrono 가 없고, 잰 값이 흘러갈 길 (통계) 만 있다
- 서버 쪽에서 창을 계산: 누적만 보내면 받는 쪽이 앞 값을 기억해야 하고, 다시 접속 · 어댑터 다시 만들기를 받는 쪽이 알 수 없다
- 표 상한 64: 컨트롤 메시지 64 KB 안 (줄 하나 ≤ 약 200 바이트), 팩의 시스템 수는 보통 수십
- 누적 최대 (연료 · 시간): 드물게 튀는 호출을 놓치지 않는다 (창 평균만으로는 묻힌다)
```

## 결과

- 얻는 것: 게임을 돌리면서 서버 · 클라이언트 스크립트 시스템의 호출 빈도 · 연료 · 시간을 본다 (로컬 · 원격 같은 표).
- 포기하는 것: 시스템 안의 함수별 프로파일 (샘플링 · 계측) · 기록 그래프 · 에디터에서 시스템 끄고 켜기 — [계획].
- 위험: 프로토콜 14 — 옛 클라이언트는 접속하지 못한다 (버전 검사가 거절). 시간은 그 기계 · 빌드 (Debug 는 몇 배 느리다) 의
  값이라 비교는 같은 조건에서만. 호출마다 시계 두 번 (steady_clock) 의 비용은 측정 안 함 — 스크립트 호출 (수 µs 이상) 에 비해 작다고 추정.

## 대안

| 대안                                      | 기각 사유                                                                 |
|-------------------------------------------|---------------------------------------------------------------------------|
| core 의 어댑터가 steady_clock 을 직접     | 시뮬레이션 코드가 벽시계를 부른다 — 04 의 규칙을 경계가 아니라 약속으로 지킨다 |
| ISystemProfiler 에 스크립트 콜백을 더하기 | 프로파일러가 틱마다 바깥에서 넘어와야 하고 시스템 번호가 Native 와 겹친다     |
| 누적만 보내고 클라이언트가 창 계산        | 다시 접속 · 어댑터 다시 만들기를 받는 쪽이 알 수 없다                        |
| 표를 admin 에게만                         | 서버 성능 정보는 이미 모두에게 (TPS · 틱 시간) — 역할마다 메시지가 갈라진다    |
| 새 메시지 (ScriptStats)                   | 1 초 통계와 같은 주기 · 같은 창이라 따로 둘 까닭이 없다                       |

## 재검토 조건

함수별 프로파일이 필요할 때 (VM 계측 · 샘플링 — 새 ADR), 시스템이 64 개를 넘는 게임이 나올 때 (표 나누기 · 상위 N), 시계 비용이
측정으로 문제일 때.
