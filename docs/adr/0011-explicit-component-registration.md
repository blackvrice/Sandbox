# ADR-0011. 컴포넌트는 카탈로그에 명시적으로 등록한다

- 상태: **Accepted** · 날짜: 2026-10-05
- 관련: [02-ECS](../02-ECS.md) 9장, [ADR-0002](0002-custom-sparse-set-ecs.md)

## 맥락

컴포넌트는 두 가지 방식으로 쓰입니다.

```text
정적 경로   reg.emplace<Transform>(e)  — 타입을 컴파일 시점에 안다. ComponentTraits<T> 만 있으면 된다.
동적 경로   세이브 로드·프리팹·에디터·해시가 "core.transform" 이라는 이름/stableId 만 보고 다룬다.
            → 이름 → (풀 생성, JSON 읽기/쓰기, 해시) 함수 표가 필요하다.
```

동적 경로의 표를 채우는 방법은 두 가지입니다: 정적 초기화로 자동 등록하거나, 명시적으로 등록하거나.

## 결정

```text
1. SBX_COMPONENT(Type, "name", version, flags) 는 ComponentTraits<Type> 특수화만 만든다 (정적 경로, 컴파일 타임).
2. 동적 경로용 ComponentCatalog 는 명시적으로 채운다:  catalog.add<T>()
   엔진 컴포넌트는 comp::registerCoreComponents(catalog) 한 곳에서 등록한다.
3. 카탈로그는 stableId 정렬을 유지하고, 같은 이름 재등록·stableId 충돌을 오류로 돌려준다.
4. Registry 는 카탈로그를 몰라도 동작한다. 동적 풀은 Registry::adoptPool(info.makePool()) 로 넣는다.
```

## 근거

```text
- 정적 라이브러리에서 아무도 참조하지 않는 번역 단위의 정적 초기화는 링커가 버릴 수 있다.
  "어떤 컴포넌트는 가끔 등록되지 않는다"는 버그는 세이브 로드가 조용히 Opaque 로 떨어지는 형태로 나타난다.
- 정적 초기화 순서는 플랫폼·링크 순서마다 다르다. 카탈로그 내용과 순서는 실행마다 같아야 한다.
- 명시적 등록은 "이 월드(서버/클라/도구)가 어떤 컴포넌트를 아는가"를 코드 한 곳에서 읽을 수 있게 한다.
  서버가 render.* 를 모르는 것(Opaque, 02-ECS 9.5)도 이 목록의 차이로 표현된다.
```

## 결과

- 얻는 것: 결정적인 카탈로그, 등록 누락이 테스트로 드러남, 링커 의존 없음.
- 포기하는 것: 컴포넌트를 새로 만들면 등록 함수에 한 줄을 추가해야 한다 (잊으면 동적 경로에서만 못 찾는다).
- 위험: 등록 누락 → Phase 5 의 콘텐츠 검증기(V3)가 "모르는 컴포넌트"로 보고한다.

## 대안

| 대안                                             | 기각 사유                                                                               |
|--------------------------------------------------|-----------------------------------------------------------------------------------------|
| 정적 초기화 자동 등록 (inline 변수, 생성자 트릭) | 위 근거 1·2                                                                             |
| 매크로가 전역 목록에 X-macro 로 추가             | 모든 컴포넌트 헤더를 한 파일이 include 해야 함 — 사실상 명시적 등록과 같고 덜 읽기 쉽다 |
| C++26 정적 리플렉션으로 자동 수집                | 세 툴체인 지원 전 (ADR 재검토 조건)                                                     |

## 재검토 조건

세 플랫폼 컴파일러가 C++26 리플렉션을 안정 지원하고, 그것으로 컴파일 타임 목록을 만들 수 있을 때.
