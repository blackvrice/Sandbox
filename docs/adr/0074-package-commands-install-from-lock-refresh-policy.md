# ADR-0074. 패키지 명령 — install 은 잠금 그대로 (캐시 → 소스 확인), update · add · remove 의 바뀌어도 되는 팩, path · git 의존은 설치해야 연다

- 상태: **Accepted** · 날짜: 2026-10-27
- 관련: [ADR-0071](0071-v0-4-package-manager-scope-pack-as-package-single-version-resolution.md) 5 · 7 (잠금 · CLI),
  [ADR-0073](0073-lockfile-format-install-folder-content-packs-unlocked.md) 7 (매니페스트와 잠금의 일치는 M3-T3),
  [09-SERIALIZATION](../09-SERIALIZATION.md) 12장, [15-BUILD](../15-BUILD.md) 7장, [18-PLATFORM](../18-PLATFORM.md) 5.2 · 6.4

## 맥락

M3-T2 까지 잠금 파일 · 설치 트랜잭션 · 열기 확인 (P8) 이 있다. 남은 것: 사용자가 부르는 명령 (ADR-0071 7 — add · remove · update ·
install), "잠금 그대로" 의 뜻 (캐시가 없을 때), 한 팩만 바꾸는 명령이 다른 팩을 몰래 바꾸지 않게 하기, 매니페스트를 고친 뒤 낡은
잠금으로 여는 일, 그리고 M1-T2 이 임시로 둔 "path · git 의존도 content/ 에서 찾는다" 를 끝내는 일.

## 결정

```text
1. sbx install <프로젝트>: 잠금이 없으면 해결해서 설치하고 잠금을 만든다. 있으면 잠금 그대로 — 먼저 매니페스트와 맞는지
   (checkLockMatches: 의존마다 잠금에 있고 소스 종류 · path · git · rev 가 같다, 잠금의 팩은 모두 매니페스트에서 닿는다 — 아니면
   거절 "sbx update"). 팩마다 사용자 캐시에서 digest 로 찾고 (오프라인), 없으면 소스를 다시 받아 digest 가 잠금과 같을 때만 쓴다
   (다르면 거절 — 잠금은 바꾸지 않는다). 잠금 파일은 같은 바이트로 다시 쓰인다
2. sbx update <프로젝트> [<팩>]: 다시 해결해 설치하고 잠금을 새로 쓴다. 팩을 주면 잠금의 다른 설치 팩은 digest 가 그대로여야
   한다 (아니면 "'x' 도 바뀐다 — 모두 갱신은 sbx update" 로 거절). 새로 생기거나 빠지는 팩은 언제나 된다
3. sbx add <프로젝트> <팩> [--path p | --git URL --rev r] [--version 범위]: 매니페스트 dependencies 에 더하고 (schemaVersion 은
   3 이상으로, 매니페스트 규칙 P7 은 다시 읽어서 본다) update <팩> 과 같이 설치한다. 이미 있는 팩이면 거절. 소스가 없으면
   content/ 의 팩 (설치하지 않고 잠금에 기록만)
4. sbx remove <프로젝트> <팩>: dependencies 에서 빼고 다시 해결 — 남는 설치 팩은 그대로여야 한다 (2 의 규칙, 바뀌어도 되는 팩 없음)
5. 매니페스트는 설치가 성공한 뒤에 쓴다 (원자적). 설치가 실패하면 매니페스트 · 잠금 · 설치 폴더 모두 그대로
6. 열기 · 검사 P8 에 더한다: 잠금이 매니페스트와 어긋남 (1 의 규칙), 잠금이 없는데 path · git 의존이 있음 ("설치하지 않았다 —
   sbx install"). M1-T2 의 "path · git 의존도 지금은 content/ 에서 찾는다" 는 끝낸다 — content/ 에 같은 id 의 팩이 있어도
   path · git 의존은 설치해야 연다 (소스 없는 의존만 content/)
7. 종료 코드: 성공 0, 매니페스트를 읽을 수 없거나 형식 오류 1 · 2 (check 와 같은 뜻), 해결 · 설치 · 인자 실패 2. 출력은
   "설치: .sandbox/packages 에 팩 n · 잠금 sandbox.lock 팩 m [· 매니페스트 갱신]" 과 잠금의 팩마다 한 줄
```

## 근거

```text
- 캐시 → 소스 확인: 같은 잠금 = 같은 바이트. 캐시는 digest 로 찾으니 오프라인 · 다른 머신에서 그대로 재현되고, 캐시가 없으면
  소스가 잠금과 같을 때만 쓴다 (몰래 다른 버전으로 설치하지 않는다 — npm ci · cargo --locked 와 같은 태도)
- 한 팩 명령의 보호: add · update <팩> · remove 가 다른 팩을 바꾸면 사용자가 모르는 남의 코드가 들어온다. 막고 명시적 update 로
- 설치 필수 (6): 잠금이 재현의 근거이므로 path · git 의존은 잠금 · 설치 폴더를 거쳐야 한다. content/ 에서 찾던 임시 규칙은
  같은 id 의 다른 팩을 조용히 쓰는 길이었다
```

## 결과

- 얻는 것: 다른 제작자의 팩을 명령 하나로 더하고 · 빼고 · 갱신하고, 잠금 하나로 다른 머신 · 오프라인에서 같은 설치를 만든다.
  어긋난 매니페스트 · 잠금 · 설치는 열기 전에 P8 로 거절한다.
- 포기하는 것: path · git 의존을 content/ 에 직접 두는 지름길 (M1-T2 시험의 기대값을 소스 없는 의존으로 바꿨다).
- 위험: update 가 path 소스를 다시 읽을 때 그 폴더가 바뀌었으면 (줄 끝 변환 포함 — ADR-0072 위험) digest 가 달라져 잠금이
  바뀐다. 매니페스트 쓰기가 설치 뒤에 실패하면 잠금이 매니페스트와 어긋난다 — 열기가 P8 로 알리고 sbx install · update 로 고친다.

## 대안

| 대안                                         | 기각 사유                                                                    |
|----------------------------------------------|------------------------------------------------------------------------------|
| install 이 잠금이 낡았으면 자동으로 다시 해결 | 사용자가 모르게 남의 팩이 바뀐다 — 명시적 update 로                           |
| 캐시에 없으면 소스 그대로 설치 (확인 없음)    | 같은 잠금으로 다른 바이트 — 재현이 깨진다                                     |
| add · remove 가 매니페스트를 먼저 쓴다        | 설치가 실패하면 매니페스트만 바뀐 프로젝트가 남는다                           |
| path · git 의존을 content/ 에서도 찾기 (M1-T2) | 같은 id 의 다른 팩을 조용히 쓴다 · 잠금이 재현의 근거가 아니게 된다           |

## 재검토 조건

레지스트리 (v0.6) 가 들어와 범위로 버전을 고르게 될 때 (update 의 뜻이 "범위 안 최신" 이 된다), 여러 팩을 한 번에 add 하고 싶을 때.
